## 二、这一步真正解决了什么

**"界面完全自己写"落地了**。之前三种形态是：

| 入口 | 窗口 | 界面 | 3D |
|---|---|---|---|
| `主程序.py` | 官方 Studio | 官方 ImGui + 自研面板 | 官方 Filament |
| `主程序Web.py` | 无（外部浏览器） | 浏览器里的 React | ❌ 占位 |
| **`主程序窗口.py`** | **我们自己的** | **窗口内 React** | **✅ 原生** |

也就是说：界面**不再依赖官方窗口**，也不再依赖外部浏览器，而 3D 仍然是真原生渲染
（不是网页里画的运动学回放）。

## 三、踩到的坑（这一节是本次最有价值的部分）

P2 已经踩过 7 个坑（见 P2 结论）。P3 又踩了 **5 个**，其中两个各花了很久：

### 坑 8：`NSTimer` 的 target-selector 在本机**完全不触发、也不报错**

`NSTimer.scheduledTimerWithTimeInterval_target_selector_userInfo_repeats_` 排上之后
`isValid()` 返回 True，**回调永远不来**。中文方法名（`画一帧_:`）与 ASCII 名
（`probeTick_:`）都试过，都不触发，且**没有任何错误输出**。

它还能伪装成"能跑"：`setNeedsDisplay_` 是**窗口系统**在驱动，所以界面看着在刷新，
于是 P2 spike 的"350 帧"和验收里的"60.1 fps"都成立 —— 而真正依赖定时器的东西
（每帧状态同步、命令搬运）从头到尾没跑过。

> **判别方法（一分钟）**：往任何"看起来能跑"的界面里插一个 0.8 秒一次性定时器，
> 看它打不打印。不打印 = 这条路不可用。
>
> **解法**：用 CoreFoundation 的 `CFRunLoopTimer`（纯 C 回调，不过 PyObjC 选择器）——
> 见 `软件/定时器.py`，它同时把定时器加到 `kCFRunLoopDefaultMode` 与 common modes。

### 坑 9：委托方法里抛异常 = **静默失效**

AppKit 回调里抛出的 Python 异常会变成 ObjC 异常，输出一行
`<class 'NameError'>: name 'xxx' is not defined`，
**而且异常之后的代码全部不执行**。

本次两次"定时器死活不触发"，真因都是我在 `applicationDidFinishLaunching_` 末尾
插的代码有 `NameError`（先是 `定时器`、后是 `记诊断` 未定义）——
于是"起定时器"那两行**从来没被执行到**。

> **教训**：delegate 里任何改动之后，都要确认它**末尾真的执行到了**。
> 本文件为此内置了 `记诊断()`（`驭臂_宿主诊断=/tmp/宿主.log`），
> 关键节点写文件，不受 stdout 被占/进程早退影响。

### 坑 10：`addObserver_selector_name_object_` 传的是**选择器字符串**，不是 Python 方法名

写 `"窗口改尺寸_:"` 会在**有 resize 时**报 `unrecognized selector sent to instance`
（不是启动时，所以很容易漏）。正确写法是 `"窗口改尺寸:"`（冒号表示参数）。

### 坑 11：`mujoco.Renderer` 的"建"与"用"必须**同一个线程**

在装载线程建、在渲染线程用，会**卡死在第一次 `render()` 里**（不报错、不返回）。
→ 渲染器改到渲染线程开头创建。

### 坑 12：渲染线程里**忙等**会饿死主线程

`while True: if not 该渲染: sleep(0.004)` 这种写法看着无害，实测让主线程的
渲染/绘制一帧都出不来。→ 改用 `threading.Event.wait(0.1)`。

### 坑 13：双击 `.app` 首次会弹 **"想访问桌面文件夹"**，不点「允许」就永远卡住

症状极具误导性：**进程活着、日志只有一行、什么错都不报**。
`sample` 抓到的栈是 `init_import_site → open()` —— 连用户代码都没跑到，
看起来像"Python 启动坏了"。

真因是 **macOS TCC**：整个包在 `~/Desktop/驭臂` 下，而**桌面是受保护目录**。
从 LaunchServices（双击图标）启动的进程没有任何 TCC 授权，
第一次读 `.venv` 里的文件就会触发系统授权对话框，`open()` 一直等到用户点击为止。

> **判别**：`sample <pid> 1` 看栈是否停在 `open()`；或者直接看屏幕上有没有那个对话框。
> **处理**：点「允许」（同一个 `.app` 只需一次）。重新打包会换掉 bundle 身份，会再问一次。
> **旁证**：同一份代码从终端跑**从不触发** —— 因为终端进程早已被授予桌面访问权。
> 用 `env -i` 模拟最小环境也正常，所以这个问题**不能靠"复现环境变量"复现**，
> 必须真的经 LaunchServices 启动才会出现。

启动脚本里已加一行提示（`启动日志.txt` 第二行），免得下次又当成"程序坏了"。

### 坑 14：**原生界面（官方 ImGui 版）打不开了** —— 函数里的重复 `import X as Y`

改 P3 时我在 `启动.启动外壳()` 的**无窗分支**里写了 `import Web桥 as _Web桥`，
而模块顶部（第 48 行）**已经**有 `import Web桥 as _Web桥`。

Python 的作用域规则是：**只要函数体里出现过赋值（`import…as` 也算），这个名字在
整个函数里就是局部变量**。于是函数靠前的 `_Web桥.默认端口`（第 268 行）直接炸：

```
UnboundLocalError: local variable '_Web桥' referenced before assignment
```

**最阴的地方**：这段代码只在**有窗模式**执行 —— 而 P3 全部验证走的都是无窗模式，
所以"新窗口一切正常、老的原生界面却打不开"，我一度以为是 `.app` 的授权问题。

> **判别**：`./.venv/bin/python 软件/主程序.py`（前台跑，直接看 traceback）。
> **修法**：删掉函数内那次重复 import，用模块级的那份。
> **防复发**：已加静态检查（下面"回归"一节），扫出函数内所有
> "先引用、后局部导入"的别名 —— 目前 0 处。

### 另外两条（不是新坑，但 P3 又撞上）

* **方法名会决定它是否被注册成 ObjC 选择器**（规则见 `objc/_transform.py`
  的 `default_selector()`：名字里第 2 个字符起含 `_`、且不以 `_` 结尾 → 纯 Python 方法）。
  本次反复踩：`同步状态`（无下划线）报 "expects 0 arguments"、
  `同步状态_`（尾下划线）报 "expects 2 arguments"、`_按需开缓冲`（前缀下划线）
  也报 0 参 —— 三种都不行，**只有中间下划线**（`同步_状态`）才对。
* **"无窗"形态下发布器用的是不存在的 `发送`**：`模型状态/参数表/辨识状态/指标`
  四个发布器都写 `发布器(发送, ...)`，而 `发送` 只是**有窗分支的局部函数** →
  `NameError` → 整段装配失败 → 界面永远"后端还没有报模型"，而 3D 照常渲染。
  → 统一改走 `发送出口`（结构上就是为"实现可换"而生的）。
  这条直接导致**界面与后端数据不通**，是 P3 的第二个大坑。

## 四、现在的能力与边界（诚实清单）

**能用**：宿主窗口、真 3D 视口 + 轨道相机、Web 界面（模型/项目/指标/参数/算法库/辨识）、
命令上行（WebSocket 带回执）、断线重连。

**还没做**：

| 项 | 说明 |
|---|---|
| 官方那 19 个 ImGui 面板 | 不在这个窗口里（它们画在官方窗口）。能力由 Web 界面覆盖，尚未一一对齐 |
| 九项功能 | 轨迹规划 / Diagnose / Deploy / SystemMonitor / 插件市场 等仍未实现 —— 界面如实标着"未接入" |
| 视口拖拽机器人 | 相机有了，拾取/拖拽还没做（属工程量） |
| Windows | 按用户要求本期不处理 |

**未验**：多显示器/不同缩放比下的像素对齐（本机是 2× Retina）；长时间（>1 小时）内存曲线
（P2 验收里 30 秒尺度是 +0 MB）。

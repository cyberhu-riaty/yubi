## 0. 怎么读这份规格

### 0.1 九项不是九个独立功能

产品清单是九项，但**工程上不是九个独立模块**。先把这条说清楚，否则后面每一项的估算都会被重复计算：

```
                    ┌─────────────────────────────┐
                    │  L0 观测核心 + 状态契约      │  ← 一份采集，三个消费者
                    │  （探针 / 环形缓冲 / schema）│
                    └──────┬───────┬───────┬──────┘
                           │       │       │
                    ┌──────▼──┐ ┌──▼────┐ ┌▼──────────┐
                    │5 诊断   │ │7 系统 │ │9 状态栏    │
                    │Diagnose │ │Monitor│ │StatusBar   │
                    └─────────┘ └───────┘ └────────────┘
```

L0 **一次实现**，被第 5、7、9 项共用（全景曲线是同一份数据的不同视图）。
**如果按"三个模块各写一遍采集"来做，这部分工作量会凭空膨胀 2.5 倍，而且三处数据必然互相对不上。**

同理，第 8 项（插件市场）的"清单格式 / 信任 / 依赖"与现有 `项目/*.json` + `算法库/` 的插件装配机制是**同一套东西的延伸**，不是新建一套。

本文件后面给出的合计估算（§10.3）**已经去掉了这层重复**。

### 0.2 一个必须先钉死的架构前提

新界面用 Web 技术重建，但**物理引擎和渲染底座不动**。LE 报告 §7 已明确：自研物理引擎不可行（13.0 万行 C + 十余年积累，一碰接触/摩擦即失真，直接作废"参数辨识 + sim2real"这条主线）。

本规格隐含的架构（第 1、2、5、7 项的全部设计都建立在它上面）：

| 层 | 去留 | 说明 |
|---|---|---|
| MuJoCo C 引擎（`mj_step` / 接触 / 求解器） | **保留** | 主线的根，不动 |
| 我方 Python 算法层（`算法库/`、装配器、参数辨识、录制） | **保留** | 已有 514 项断言保护 |
| 我方 Python 桥接层（`指标桥` / `参数桥` / `模型桥` / `辨识桥` / `录制桥`） | **保留语义，换传输** | 现在是 MuJoCo Studio 的 `Snapshot` 消息通道；改为进程内事件总线 + 对外 WebSocket |
| `mujoco.experimental.studio`（官方 ImGui 工作台，L4） | **移除** | 这是被替换的那一层。当前**唯一**直接 import 它的文件是 `软件/插件系统.py`，边界干净 |
| `mujoco.Renderer` 离屏渲染 | **保留（降级为可选路径）** | 实测 1280×720 **7.9 ms/帧 = 126 fps**，够做录制/视频导出/服务端渲染备份 |

**这条前提带来的一条真实收益（应当写进对外口径）**：现有 `0.86×` 的时间比有一半是官方节拍器造成的——LE 报告 §6.2 实测 `StepControl.set_speed()` 上限被钳在 100%、节拍由墙钟驱动。脱离 Studio 后，节拍由我们自己控制（已有实测支撑：定频 1000 Hz 闭环占空比 7.07%、0/2000 超期；macOS 必须用 `sleep + 忙等` 混合等待）。**"实时因子"从一个偶然结果变成我们的一个可测、可控指标**——这正好是第 7 项要展示的东西。

## 1. 轨迹规划（Trajectory Planning）

### (a) "完整实现"的段落定义

**完整实现 = 用户可以给出一个几何路径描述（关节航点 / 笛卡尔航点 / 笛卡尔基本元 / 导入的 CSV），软件在真实关节限位与运动学约束下算出一条时间参数化轨迹（位置/速度/加速度/加加速度的时间序列 + 路径参数 s 上的速度包络），把这条轨迹作为**离线产物**存下来，再由一个独立的跟踪控制器在仿真里忠实执行；规划成败、约束是否贴边、哪一段是瓶颈，全部有数字和图形证据；同一路径可以换约束重规划并与旧结果逐点对比。**

三件必须说清楚的事，它们直接决定这个功能"真"还是"假"：

**① 仿谁、不仿谁。** 参考实现的算法分工值得学，建模缺陷必须纠正：

| 环节 | 参考实现做法 | 我们的规格 |
|---|---|---|
| 路径准备 | `ssMode='arc'` 用末端弧长参数化；`'time'` 等距（LE 报告 §2.4.1） | **保留**，s ∈ [0,1] 归一化弧长（笛卡尔路径）或归一化关节路径长度（关节路径） |
| TOPPRA | 时间最优参数化，关节速度约束 + 关节加速度约束 + 外层 `RobustLinearConstraint`（`du=1e-3, dx=5e-2, dc=9e-3`） | **保留**，但**约束必须在关节空间显式声明且可导出**（见下文"约束"） |
| MVC | `X[:,1]` 速度上包络，**既当展示曲线又当分段依据**（局部极小值成为段交界速度） | **保留这个思路**——它是参考实现里最干净的一处设计 |
| Ruckig | 对路径参数 s 做 **1-DoF jerk 受限整形**，带 4 级回退速度阶梯 | **保留**，但回退阶梯必须**每一步都告知用户**（"第 3 级回退：s 段 12 的 jerk 上限放宽 20%"），不能静默降级 |
| 映射回关节 | `qs = path(ss)`，`qd/qdd = np.gradient(...)` | **必须改**。`np.gradient` 算出的速度/加速度**不保证满足约束**，只是数值微分。我们要**解析求导**（路径为 B 样条/样条时用其导数），并对结果**逐点回代校验** |

**② 必须纠正的建模错误（照抄就错）。** 参考实现的 `v_max / a_max / j_max`（`pipeline.py:39-42`）是**路径参数 s 空间的量，不是关节空间的量**，但界面上标着"关节速度约束"——**标签与作用域不一致**（LE 报告 §2.4.1 已指出）。我们的规格：

- **关节空间约束**（`q̇_max, q̈_max, q⃛_max`，来自 `mjModel.jnt_range` 与用户覆盖）**是第一类约束**，进 TOPPRA；
- **路径参数空间的整形上限**（Ruckig 用的 `ṡ_max, s̈_max, s⃛_max`）是**第二类、派生的**——它必须由第一类约束**推导**出来（`ṡ ≤ min_i(q̇_max,i / |dq_i/ds|)`），**不允许**作为独立滑杆暴露给用户；
- 界面上如果出现"s 空间速度上限"这个数，它旁边必须显示"由关节速度约束推导，当前绑定关节 = J3"。

**③ 结果不能直接接到 `ctrl[:]`。** 这是 LE 报告 §B.3 的核心结论，必须写进界面文案：规划器输出的是**期望关节轨迹**，MuJoCo 要的是力矩或位置指令，语义对不上。正确链路：

```
路径描述 → 离线规划（TOPPRA + MVC + 分段 Ruckig） → (t, q, q̇, q̈, q⃛) + s 剖面
                                                          ↓ 存成轨迹资产
                       跟踪控制器插件（前馈 q̈_des + PD）→ data.ctrl[:]
```

复用已有的 `算法库/通用/关节pd控制.py` 作为跟踪器内核（它是现成的，且已带重力补偿）。

### (b) 功能拆解

**B1 用户输入（四条入口，缺一不可）**

| 入口 | 形态 | 备注 |
|---|---|---|
| 关节航点表 | `[q1..qn] × m` 行表格，可直接编辑、粘贴；n 随模型 | 最基本入口 |
| 笛卡尔航点表 | 位置 + 姿态（四元数或 RPY） | 需要 IK，见 B4 |
| 笛卡尔基本元 | 直线 / 圆弧 / 圆（在给定平面内） | 圆弧直接决定 `ssMode='arc'` 是否有意义 |
| CSV 导入/导出 | ≥ 两种表头：`t,q1..qn`（时间序列）与 `q1..qn`（航点）；**7 轴/2 轴都要能读** | 参考实现硬编码 `J1..J6` 表头且限位校验强制 6 值（LE 报告 §B.2）——**这条必须参数化** |

**B2 约束面板（必须区分"关节量"与"派生量"，见上）**

- 关节位置上下限（默认从 `mjModel.jnt_range` 读，只读 + 可覆盖，覆盖要留痕）
- 关节速度上限、加速度上限、**加加速度上限**（jerk）
- 末端笛卡尔速度/加速度上限（转成关节量后并入约束集；转换失败要在界面上报"该约束在当前姿态不可行，已忽略并记录"）
- 力矩上限（来自 `mjModel.actuator_ctrlrange`）——**作为事后校验项，不进 TOPPRA**（TOPPRA 做的是运动学时间最优，不含动力学；把它当动力学约束用是错的，界面必须写这句）
- 规划时长上限 / 采样周期（默认 1 ms，与录制 100 Hz 解耦）

**B3 规划内核**

- `规划器` 抽象接口（**参考实现没有策略接口、换算法要动 5 处，见 LE 报告 §2.4.2——我们必须有注册表**）：

```python
class 轨迹规划器(Protocol):
    名称: str; 版本: str
    输入模式: tuple[str, ...]        # "关节航点" | "笛卡尔航点" | "基本元" | "时间序列"
    支持自由度: tuple[int, ...] | None  # None = 任意；用于 2/6/7 轴声明
    def 能规划(self, 模型, 路径, 约束) -> str: ...   # 返回 "" 或拒绝原因（沿用 模型兼容性 的既有约定）
    def 规划(self, 模型, 路径, 约束) -> 规划结果: ...
```

- 参考实现移植为**其中一个实现**（`TOPPRA_MVC_Ruckig`），不是唯一实现。另需一个**平凡的兜底实现**（`梯形速度插值`，纯 numpy，无外部依赖）——它的存在让"规划器插件崩了"变成"降级"而不是"功能没了"。
- **许可证硬约束**：TOPPRA 默认求解器 `ecos` 是 **GPLv3**，与本项目 MIT 分发冲突；且实测换 `seidel` 不可行（算法外层包了 `RobustLinearConstraint` 产生二阶锥约束）。**已实测的解法**：`cvxpy + Clarabel`（均 Apache-2.0），数值结果与 ecos **完全一致**（时长差 0.0000 s、关节角差 0.000000 rad），代价是**慢约 32 倍**（5.19 s → 164.91 s）。→ **规格：默认走 `cvxpy + Clarabel`，`ecos` 作为本机可选加速路径（检测到且用户显式开启才用），并在"关于"里记录当次用的哪个求解器。** 离线规划慢 32 倍可以接受，GPL 污染不可以。

**B4 逆运动学与冗余（2/6/7 轴都成立的地方）**

- **不做通用 IK 求解器**，做**路径级 IK**：沿笛卡尔路径离散成 N 个位姿，逐点解 IK，**并要求解之间连续**（用上一解做初值 + 关节空间距离惩罚选分支）。
- 7 轴冗余：暴露 1 个冗余自由度（肘部/臂角），提供"手动指定臂角"与"用零空间优化最优臂角"两种模式。
- 6 轴：在奇异位形附近给出**分支跳变警告**；无法保持连续时**必须拒绝该路径并指出 s 区间**，不允许静默给出一条会突然翻腕的轨迹。
- 2 轴：不做 IK（位姿不足），走关节路径 + `mj_forward` 校验末端位置。
- 硬件无关实现：用 `mj_kinematics` + `mj_jac`（数值/解析雅可比），**不引入 roboticstoolbox**（LE 报告 §B.2 已确认它只用于拿模型，而 MuJoCo 自带更权威的模型）。

**B5 碰撞（诚实划界）**

参考实现没有碰撞检查。**第一版不接 FCL/hpp-fcl**，而是：

- 用 MuJoCo 自己的碰撞管线做**离散采样校验**：把轨迹按 1 ms 采样，逐点代入 `mj_forward` 后读 `data.ncon` + 接触对（`data.contact[i].geom1/geom2`），**排除"本来就在接触的几何对"**（机器人底座与地面），报出碰撞发生的 `s` 区间与几何对。
- 成本：一次 16 s 轨迹 ≈ 16 000 次 `mj_forward`；实测 `mj_step` 是 3.39 µs，`mj_forward` 更便宜 → **单次校验在 0.1 s 量级**，可以直接做。
- **不做**：连续碰撞检测（CCD）、避障重规划（把碰撞作为约束反馈给规划器迭代）。这两条明确标注"未实现"，而不是画一个"碰撞检测 ✓"的假徽章。

**B6 输出与可视化（"看得见的证据"）**

输出数据（存成轨迹资产，格式见 (c)）：

- 时间序列：`t, q[n], q̇[n], q̈[n], q⃛[n]`（默认 1 ms 等间隔）
- 路径剖面：`s(t), ṡ(t), s̈(t)`，以及 **`ṡ(s)` 这条 MVC 上包络**
- 约束贴合报告：每个关节的 `max|q̇_i| / q̇_max,i`、`max|q̈_i| / q̈_max,i`，**指出 100% 贴边的那个关节与 s 位置**（这才是"时间最优"的证据）
- 分段报告：每段的 `(s_start, s_end, 时长, 用了哪级 jerk 回退)`
- 规划报告：求解器名、耗时、迭代/回退次数、IK 分支切换次数、碰撞校验结果

可视化（同一份数据，四种视图，**必须共用时间轴与光标**）：

1. **s 剖面图**：`ṡ(s)` 曲线 + MVC 上包络 + 分段交界竖线 + 约束贴合点标记
2. **关节轨迹图**：n 行（每关节一行）× (q, q̇, q̈) 三列的网格，每行叠加限位/限速水平线
3. **时序图**：`q(t)` 全关节叠加 + 总时长轴 + 当前播放头
4. **3D 联动**：3D 视口里同时显示**实际姿态（本体）**与**规划姿态（幽灵）**，跟随播放头；幽灵超差时变色
5. **时间对标条**：本轨迹 vs 上次轨迹的时长/峰值速度并列条形（对比功能的最小形态）

**B7 执行**

- 规划结果是**资产**（落盘），执行是**加载一个资产并跟踪**：
  - 新增 `算法库/通用/轨迹跟踪.py`：读轨迹资产 → 按仿真时间取期望 `q_d, q̇_d, q̈_d` → 力矩 = `q̈_d` 前馈（含质量阵/重力：`M(q)q̈_d + C(q,q̇)q̇_d + g(q)`，MuJoCo 里用 `qfrc_bias` + `mj_fullM`）+ PD 反馈 → 写 `ctrl[:]`
  - 时间缩放 `[0.1×, 2×]`、暂停/继续/单步、从头/从当前仿真状态起步（后者需要重算前馈，第一版只允许从头）
  - 跟踪误差**实时回传给诊断**（第 5 项），超差阈值可设
- **不允许**把规划结果直接写 `qpos`（那是作弊：绕过动力学，"轨迹跟踪"就没有意义了）。

**B8 失败面（必须逐条有明确出口，不允许"失败就沉默"）**

| 失败 | 界面表现 | 用户可做什么 |
|---|---|---|
| 路径点超关节限位 | 拒绝 + 高亮越限的关节与行号 + 越限值 | 改航点 / 改限位覆盖 |
| IK 无解 | 报出无解的 s 区间 + 最近的可解姿态 | 改姿态容差 / 改路径 / 换臂角 |
| IK 分支跳变 | 定位到跳变点，标出前后两解 | 强制分支 / 拆分路径 |
| 时间最优失败（TOPPRA 不可行） | 报出是哪个约束、哪个 s 区间导致 | 放宽指定约束（一键"放宽 10% 重试"） |
| Ruckig 用了回退 | 分段报告里逐段标注第几级回退 | 接受 / 手动指定段交界速度 |
| 规划超时 | 进度条 + 取消按钮（`cvxpy` 路径可能 3 分钟） | 取消；切小求解器或分段规划 |
| 碰撞 | s 区间 + 碰撞几何对 + 一键跳到该姿态 | 改路径 |
| 轨迹超出力矩上限 | 事后校验报告（明确标"运动学可行、动力学超限"） | 降速度/加速度约束重规划 |

**B9 保存与对比**

- 轨迹资产目录 `输出/轨迹/<轨迹名>/`：`轨迹.npz` + `轨迹.json`（元数据/报告）+ `预览.png`（静态图，便于不看软件也能比对）+ `指纹.txt`（输入路径 + 约束 + 规划器版本 + 求解器 + 模型哈希的内容寻址 hash）
- **对比**：选两条轨迹 → 时长/峰值/贴边关节/样本逐点最大差 表格 + 曲线叠加图
- 工程纪律沿用现有做法：**每个轨迹资产自带 hash**，纳入 `工具/验证/` 的断言集

### (c) 数据/状态模型

```
规划请求 PlanningRequest
  ├ 模型引用: {路径, 内容hash}          ← 复用现有 项目/*.json 的 模型 字段语义
  ├ 路径描述: 关节航点 | 笛卡尔航点 | 基本元 | 时间序列CSV
  ├ 约束集: 关节{qmin,qmax,qd_max,qdd_max,qddd_max}
  │         笛卡尔{vd_max,ad_max}  力矩{tau_max}  采样{dt, 时长上限}
  ├ 规划器选择: {名称, 版本, 选项}
  └ 自由度 n                     ← 一切数组都是 n，不允许出现 6

约束集 与 派生量 必须分开存：
  用户约束（权威，进 hash） / 派生量（ṡ_max 等，可重算，不进 hash）

规划结果 PlanningResult
  ├ 状态: 成功 | 部分成功 | 失败(原因枚举 + 定位)
  ├ 时间序列: (t[], q[][n], qd[][n], qdd[][n], qddd[][n])
  ├ 路径剖面: (s[], sdot[], sddot[], mvc_envelope[])   ← MVC 单独一段，供绘图
  ├ 分段报告: [(s0,s1,时长,jerk回退级)]
  ├ 贴合报告: {关节i: (峰值比, s位置)}
  ├ 诊断: {求解器, 耗时, 迭代, IK分支切换, 碰撞区间, 力矩超限样本}
  └ 指纹 hash
```

**关于自由度**：`n` 从 `mjModel.nv` / `jnt_range` 来，**任何地方出现字面量 6 都是缺陷**。规格要求一条自检：`工具/验证/` 里加一个"2/6/7 轴各跑一遍规划"的用例（2 轴用 robotiq_2f85 的两个关节或一个自造 2 轴模型，7 轴用 iiwa14）。

### (e) "假但像样"会是什么样（必须显式避免）

- ❌ 用**固定时长的三次/五次多项式插值**冒充时间最优：曲线很漂亮，但**没有任何约束投影**，关节速度峰值可能超限 3 倍。识别方法：**看有没有"贴合报告"**——真规划一定有某个关节在某个 s 位置贴到 100%。
- ❌ 只有 `q(t)` 一条曲线，没有 `ṡ(s)` 与 MVC 包络。参考实现的 MVC 之所以值得学，正是因为它**同时是可视化与分段依据**；砍掉它 = 砍掉可解释性。
- ❌ 把 `ṡ_max` 当"关节速度约束"暴露（参考实现的原话：滑杆标签与实际作用域不一致）。**照抄这个就是连缺陷一起抄。**
- ❌ 只有 6 轴能跑：CSV 强制 `J1..J6`、限位校验强制 6 值。识别方法：**拿 iiwa14（7 轴）跑一次**。
- ❌ 规划完直接把 `q` 写进 `qpos` 播放（"回放动画"）。识别方法：**规划执行时看力矩是否非零、跟踪误差是否非零**。
- ❌ 失败时静默回退到"随便给条能动的轨迹"。识别方法：**构造一条越限路径，看它是否报错**。

## 2. 3D 机器人显示（3D Robot Visualization）

### (a) "完整实现"的段落定义

**完整实现 = 3D 视口里的几何与姿态**全部由仿真侧的权威数据驱动**（不是前端自己按 URDF 重算 FK），能流畅显示任意（2/6/7 轴）已加载模型的实时运动、接触力、地面网格与光照；能切换相机与模型；能叠加幽灵目标姿态与坐标轴；能回放已录制数据（含变速拖动）；**并且有一套可验证的帧率纪律——UI 帧率与物理步进解耦，断网/卡顿时有明确降级而不是整体变慢**。

### (b) 功能拆解

**B1 几何与姿态的来源（这是本项的技术核心）**

两条路，**都做，主备关系**：

| | 路线 A（主）：浏览器端场景图 | 路线 B（备）：服务端离屏渲染 |
|---|---|---|
| 原理 | 仿真侧导出**一次**场景图（body 树 + 关节轴 + 几何 + 材质 + 网格文件），运行时每帧只发**姿态**；浏览器按姿态摆几何 | `mujoco.Renderer` 出图 → 编码 → 推给浏览器当贴图/`<img>` |
| 实测 | 姿态数据量：10~30 body × 7 float ≈ 1~2 KB/帧，30 Hz 下 **< 60 KB/s**，可忽略 | 1280×720 **7.9 ms/帧 = 126 fps**（本机实测） |
| 交互 | 浏览器原生（60 fps 相机、拾取、拖拽） | 相机必须在服务端（每次转视角要往返） |
| 保真 | 依赖前端渲染器（three.js PBR，弱于 Filament） | **与官方视觉完全一致** |
| 用途 | 主界面 | 视频导出、**"官方视角对照"**、前端渲染器不可用时的降级 |

**规格要求（这条决定"真"还是"假"）**：**姿态必须权威来自 `mjData`，不允许前端按 MJCF 重算 FK。** 具体：

- 仿真侧每帧导出 `body_xpos` / `body_xquat`（本机已验证这些字段存在且可取）；浏览器只做**父→子变换的应用**，不做关节轴旋转的重算。
- 好处：**不存在"前端算错了但看起来能动"的可能**。这一条把"3D 显示是否忠实"从"看运气"变成"看数据"。
- 代价：每帧多传约 1~2 KB/帧——**这个代价必须付**。

**B2 场景图导出（一次，模型加载时）**

从 `mjModel` 读（本机已验证字段可用）：

- 拓扑：`nbody` / `body_parentid` / `body_pos` / `body_quat`；关节 `jnt_type` / `jnt_axis` / `jnt_range` / `jnt_qposadr` / `jnt_dofadr` / `jnt_bodyid`
- 视觉几何：`geom_type` / `geom_size` / `geom_rgba` / `geom_matid` / `geom_group` / `geom_contype` / `geom_conaffinity`
- 网格：`mesh_vert`（本机实测 panda 有 **374 083 个顶点**）/ `mesh_face` / `mesh_texcoord` / `mesh_facenum`
- 材质/贴图：`mat_rgba` / `mat_texid` / `tex_*`
- 光照：`light_*`（方向、颜色、环境光）→ 前端的 PMREM 环境贴图近似

**网格资产管线（这一项的实际大头）**：`模型/` 共 108 MB、199 个文件，其中 `模型/universal_robots_ur5e/assets/upperarm_3.obj` 单个 5.1 MB。要做的：

1. **顶点去重 + Draco 或 meshopt 压缩 → GLB**（`.venv` 里没有 trimesh，需要引入；或走 Node 侧 `gltf-transform`）
2. **LOD**：至少 2 级（近景全精度 / 远景 30% 面数）
3. **材质归一化**：`.obj + .mtl`、`.stl`（无材质）、`.dae`（Panda/UR 部分资产是 DAE，需要 COLLADA→glTF 转换）
4. **不动点**：**源资产（108 MB）不进分发产物**，只进 GLB + 元数据

**B3 相机与交互**

- 轨道/平移/缩放、预设视角（正视/侧视/俯视/等轴/复位）、聚焦到选中 body
- **跟随模式**：跟随末端点 / 跟随指定 body（调试抓取时必需）
- 自由相机与"模型坐标下的固定相机"两种；相机状态持久化
- 点击拾取 body/geom → 高亮 + 显示该 body 的实时量（位置、速度、作用于它的力）
- 与官方已有的能力对齐：拖拽扰动（`mjv_applyPerturbForce` / `mjv_initPerturb`）**列为可选**——它是真能力，但需要前端实现 3D 拖拽 gizmo，成本不小，第一版标注"未实现"而不是做个假的

**B4 接触与力可视化**

- 接触点：从 `data.ncon` + `data.contact[]` 取（`geom1/geom2/pos/frame/dist`），在 3D 里画点 + 法向箭头
- 接触力：需要 `mj_contactForce` 逐个接触算（或读 `data.efc_force` 对应切片），箭头长度按力的大小
- 力阈值过滤 + 只显示选中 body 的接触（否则满屏箭头）
- 外力/扰动箭头、关节力矩箭头（力矩方向 + 颜色映射）

**B5 地面/网格/光照**

- 无限地面网格（可开关、可调间距、可调透明度），坐标轴 gizmo
- 光照：一个主方向光 + 环境光（对齐 MJCF 的 `light`）；IBL 环境贴图近似金属反射
- 阴影：可开关（**默认关**：真时工具里阴影是干扰，且开销大）

**B6 模型切换**

- 复用现有的切换链路（当前实测切换耗时 5~236 ms，见 `启动日志.txt`）：切换时前端收到"新场景图 + 清空姿态"事件，**不允许出现旧几何残影**
- 切换期间显示遮罩进度（首帧全量 GLB 下载可能几百 ms 到数秒）
- **前端不缓存模型**（缓存 = 内存泄漏 + 换模型不干净的真实来源）；只缓存 GLB 的 HTTP 层

**B7 回放（录制数据）**

- 加载 `输出/04_记录/` 的录制文件（现有 100 Hz 录制能力）
- 时间轴：播放/暂停/单步/拖动/变速（0.1×~4×）/循环/逐帧
- **拖动必须即时应答**（不是"拖完松手才跳"）：需要随机访问的索引（录制文件建立 `t → 帧号` 索引）
- 回放态与实时态**视觉必须可区分**（角标"回放中"，实时曲线灰掉）——防止用户把回放当成真跑

**B8 幽灵/目标姿态**

- 半透明幽灵 body（显示"规划/期望姿态"），与实际姿态叠加
- 幽灵与实际之间的误差可视化（连线 + 数值）
- 用途：轨迹跟踪调试、IK 校验

**B9 帧率纪律（可验收的硬指标）**

- **物理步进（500~1000 Hz）与 UI 渲染（目标 60 Hz）完全解耦**：物理线程永不等待渲染
- **显示插值**：浏览器维护最近两帧 (t, 姿态) 缓冲，渲染时线性插值 → 网络 30 Hz 也能平滑 60 fps
- **降级策略（明确三级）**：① 帧率 < 45 fps 持续 2 s → 关阴影/降 LOD；② < 30 fps → 降采样远景物；③ 断连 → 显示"数据已停止"角标 + 画面冻结（**不允许继续用旧数据插值假装在动**）
- **可验收**：监控面板（第 7 项）里显示 `UI 帧时间 p50/p99`、`数据到达间隔抖动`、`丢帧数`。**这三个数必须能在诊断里被引用**，否则"帧率纪律"就是口号。

### (c) 数据/状态模型


### (e) "假但像样"会是什么样

- ❌ **前端自己按 URDF/MJCF 重算 FK**：看起来能动、能转，但和 MuJoCo 的实际姿态**慢慢漂移**（尤其是 `free joint`、`ball joint`、有 `refsite`、有 tendon 的模型）。识别方法：**加载一个带自由关节的模型，看落地姿态是否与物理一致**。
- ❌ **只换外壳不换姿态**：切模型时只换了网格，关节角还在用旧模型的。识别方法：**切到 7 轴的 iiwa14，看第 7 轴是否真的动**。（参考实现就有这个问题：换机器人只换 3D 壳，规划恒算 ER15。）
- ❌ **回放用 `setInterval` 重新推姿态序列**：拖动时间轴卡顿、变速时抖动。识别方法：**在 4× 速度下拖动进度条**。
- ❌ **接触力可视化用"有没有碰撞"布尔值染色**：没有力的大小。识别方法：**看箭头长度是否随负载变化**。
- ❌ **帧率靠"限制网络发送频率"假装**：物理线程被渲染拖着走（现有 `0.86×` 就是这类耦合的症状）。识别方法：**把浏览器最小化跑 1 分钟，看仿真时间比是否变化**。

## 3. 参数配置表（Parameter Configuration Table）

### (a) "完整实现"的段落定义

**完整实现 = 一个带类型、单位、来源与作用域的可编辑参数表**：每一行都能回答"这个数从哪来、属于谁、改它要不要重载模型、改完影响哪些算法"；编辑有校验（类型/范围/跨参数约束/单位换算）；Apply 是**事务性**的（全成功或全回滚，并有 diff 预览）；Reset / Revert 语义明确（回到默认 / 回到磁盘上已保存的）；所有写入持久化且**可追溯**（谁改的、什么时候、旧值新值）；**参数辨识的结果能一键提升为参数表的值，并带置信区间与来源标注**。

### (b) 功能拆解

**B1 参数分类（这是"表"能不能立住的关键）**

不分清来源，表就会变成一个"什么都往里塞"的垃圾桶。规格定义**五类**，每类有独立的读写路径：

| 类 | 例子 | 作用域 | 改动代价 | 来源 |
|---|---|---|---|---|
| **A 结构参数** | body 质量、惯量、几何尺寸、关节轴、父子关系 | 模型 | **必须重载模型**（且会使辨识结果失效） | MJCF |
| **B 执行器参数** | `gainprm` / `biasprm` / `ctrlrange` / `forcelimited` / `gear` | 模型 | `mjModel` 数组可**热改**，但需重建执行器增益缓存 | MJCF |
| **C 求解器/积分参数** | `timestep` / `iterations` / `ls_iterations` / `solver` / `integrator` / `impratio` / 摩擦锥 | 模型 | 热改（`opt`） | MJCF + 界面 |
| **D 控制器参数** | KP / KD / 目标 / 插件自定义参数 | 算法 | 热改（下一控制周期生效） | 插件 `可调参数()` + 界面 |
| **E 辨识结果** | 连杆质量、质心、摩擦、电机常数 | 派生 | **只读**（是证据不是设置），可"提升"成 A 的覆盖 | 参数辨识 |

**关键区分**：A/B/C 是**模型参数**（"这台机器人是什么"），D 是**控制器参数**（"我们怎么控制它"），E 是**证据**。三类混在一张表里就必须用"作用域"列区分开，并且**Apply 时按类分组执行**（A 重载 → B/C 热改 → D 广播）。

**B2 列定义（列是可配的，但下面这些是必备）**

| 列 | 说明 | 可编辑 |
|---|---|---|
| 分组 | 关节 / 执行器 / 求解器 / 控制器 / 辨识 | 否 |
| 参数名（中/英） | 双语，沿用现有 `文案.py` + `界面文字.py` 的术语表 | 否 |
| 符号 | 如 `K_p`、`q̇_max` | 否 |
| 路径 | 规范地址，如 `jnt[3].range[0]`、`act[0].gainprm[0]`、`步进控制.KP` | 否 |
| **单位** | 显式单位字符串；**无量纲写 "1"**，不写空 | 否（选填换算） |
| 类型 | float / int / bool / enum / vec3 / 引用 | 否 |
| 默认值 | 来源原值（MJCF 值 / 插件类属性值） | 否 |
| 当前值 | 生效值 | **是** |
| 覆盖标记 | 是否被用户覆盖（视觉上必须一眼可辨） | 否 |
| 来源 | `MJCF:模型路径` / `插件:名称@版本` / `辨识:实验ID` / `用户覆盖` | 否 |
| 作用域 | A/B/C/D/E | 否 |
| 约束 | 硬范围 + 跨参数约束引用 | 否 |
| 可辨识性 | 来自辨识的设置（可辨识 / 不可辨识 / 未评估） | 否 |
| 描述 | 一句话人话 | 否 |

**为什么"单位"必须是列而不是藏在提示里**：这个项目已经踩过单位相关的坑（`工具/` 里有 urdf→mjcf 转换，`报告` 里记录过"单位/坐标检查：无"是缺口）。单位是**第一类信息**。

**B3 校验（三层）**

1. **类型/范围**：超出硬范围 → 红色 + Apply 被阻止（不是"自动钳到边界"，那会静默改用户的意图）
2. **跨参数约束**：如 `qmin < qmax`、`KD ≥ 0`、`iterations ≥ 1`、`ctrlrange` 与 `forcelimited` 一致、`timestep` 与录制频率的整除关系 → **黄色警告可强制应用**（有些约束是"通常如此"不是"必须如此"）
3. **单位一致性**：长度必须米、角度必须弧度（界面可显示度但**存储恒为弧度**——这是本文档的一条硬规定，防止度/弧度混用这类经典事故）

**B4 Apply / Reset / Revert 语义（必须写进界面文案）**

| 操作 | 语义 | 影响面 |
|---|---|---|
| **Apply** | 把草稿值提交到运行中的仿真；先算 diff，弹预览（哪些行变了、哪些需要重载、哪些会让辨识结果失效），确认后事务性执行 | 分三类执行顺序：A 重载 → B/C 热改 → D 广播 |
| **Reset（本行）** | 单行回到"默认值"（MJCF 原值 / 插件类属性值） | 一行 |
| **Reset（全部）** | 所有覆盖清空，回到默认 | 全部 |
| **Revert** | 回到"磁盘上已保存的值"（即上次 Save 的状态），丢弃未保存的草稿 | 全部 |
| **Save** | 写回 `项目/*.json`（沿用现有机制）+ 写入模型覆盖文件 | 持久 |
| **Export** | 导出为 JSON/YAML（便于版本对比与外部工具读） | 文件 |

**未保存更改**必须在状态栏（第 9 项）可见。切换模型/项目时有未保存更改 → 拦截并询问。

**B5 与参数辨识的关系（这是本项与第 5 项的接口）**

- 辨识面板产出的**不是**直接写进参数表，而是产出一个**辨识结果资产**（含：拟合参数、置信区间/协方差、残差、实验条件、数据文件 hash）
- 参数表里出现辨识结果的方式：① **E 类只读行**（显示"辨识值 + 区间"）；② 一个 **"提升为覆盖"** 按钮（把辨识值写成 A/B 类覆盖，并标注来源 = `辨识:实验ID`）
- **必须显示的三件事**：辨识值、**与当前值的差**、**置信区间**。参考项目的 `辨识参数表.json` 已经有类似结构，规格要求**加区间与实验 ID**。
- **不可辨识参数必须显式标注**：这是 LE 报告里指出的"全行业空白"，而本项目踩到过真实例子（质心位置在某类轨迹上不可辨识，所以默认只辨识 3 个连杆质量）。参数表里这类行必须显示 `不可辨识（在这段轨迹上）` 而不是一个空值或 0。
- **改了 A 类参数要让辨识结果失效**：`参数表` 与 `辨识资产` 之间用**模型 hash + 参数集 hash** 关联；hash 变了，辨识行标灰并提示"该结果基于旧参数，建议重新辨识"。

**B6 表格交互（Web 界面该有的水准）**

- 虚拟滚动（参数可能上千行：`nq × 多类`）
- 列排序/筛选（按分组、按"已覆盖"、按"有警告"、按"可辨识"）
- 多选 + 批量编辑（例如把所有关节的 `KD` 乘 1.1）
- 键盘导航（Tab/Enter/方向键）、复制粘贴（与 Excel 互通：粘贴一列数进去）
- 搜索（按中文名/英文名/符号/路径）
- 单位换算显示（度/弧度切换**只影响显示**，且有明显标记）
- **撤销/重做**（至少 20 步）——表格编辑没有 undo 是不可用的

**B7 与面板/项目的关系**

- 参数分类树侧栏（对齐现有 `参数面板.py` 的信息架构，但**不照搬 ImGui 的布局限制**）
- 参数的"草稿态"属于**项目**（不是全局），一个项目一套草稿
- 与现有 `参数桥` 的 10 Hz 参数推送衔接：**表是权威，仿真侧是消费者**；仿真侧改的参数（如插件自己更新的目标值）以"仿真侧回写"的形式回到表里，标 `来源:运行时`

### (c) 数据/状态模型

```
参数定义 ParamDef（来自模型/插件，只读）
  {路径, 中文名, 英文名, 符号, 单位, 类型, 默认值, 硬范围, 跨参数约束,
   作用域(A|B|C|D|E), 来源, 描述, 可辨识性}

参数集 ParamSet（可序列化，就是持久化的东西）
  ├ 基: {模型hash, 项目名}
  ├ 覆盖: {路径 → 值}
  ├ 草稿: {路径 → 值}          ← 未 Apply 的编辑
  ├ 运行时回写: {路径 → 值}     ← 仿真侧写回的
  └ 历史: [(时间, 用户, 路径, 旧值, 新值)]   ← 审计

应用事务 ApplyTransaction
  ├ diff: [(路径, 旧值, 新值, 影响面)]
  ├ 需要重载: bool / 失效辨识: bool
  ├ 步骤: [重载模型 | 热改MJCF | 热改opt | 广播插件]
  └ 结果: 成功 | 失败(哪一步 + 回滚是否成功)

辨识结果资产 IdentResult
  ├ 实验ID / 时间 / 数据文件hash / 模型hash
  ├ 参数: {路径 → (辨识值, 区间, 是否可辨识)}
  ├ 残差曲线 / 条件数 / 收敛信息
  └ 指纹
```

|---|---|

| B2 表格 UI（虚拟滚动、列配置、排序筛选、多选、复制粘贴、键盘） | 9 |
| B3 三层校验 + 单位系统 | 5 |
| B4 Apply/Reset/Revert/Save 语义 + diff 预览 + 事务与回滚 | 6 |
| B4 持久化（项目 JSON + 模型覆盖文件 + 审计历史） | 4 |
| B5 辨识集成（只读行、提升为覆盖、失效检测） | 5 |
| B6 撤销/重做 | 3 |
| 测试（分类正确性、回滚、单位、hash 失效联动） | 5 |
| **合计** | **44** |

**风险**

1. **参数发现器的覆盖度**：`mjModel` 有几百个字段，全部展开会淹没用户；漏掉关键字段又会让"用表配参数"变成"还得去改 XML"。对策：**先做白名单**（A/B/C 三类各挑一批真正会用的），**并在界面上明确显示"本表覆盖 N 项，模型共有 M 项"**——诚实比完整重要。
2. **热改 `mjModel` 的安全边界**：改 `gainprm` 等需要重算 `actuator_*` 派生量，MuJoCo 并没有"重新初始化执行器"的公开入口。第一版**保守策略**：B/C 类中"不能确认安全热改"的项，一律走重载路径，并在界面上标"需要重载"。**不允许**为了流畅而假装热改。
3. **重载模型会清掉仿真状态**：必须给用户明确的"这会重置机器人姿态"提示，并且**在 Apply 前自动快照当前状态**（可一键恢复）。

**风险预算：+5 人日 → 区间 44~49 人日。**

### (e) "假但像样"会是什么样

- ❌ **只有滑杆没有表**（现状的延伸）：能调但不能比、不能批量、不知道单位、不知道来源。
- ❌ **表里全是"数字"没有单位没有来源**：看起来完整，改错一次查不出来。识别方法：**看有没有"作用域"和"来源"列**。
- ❌ **Apply 后立刻改 `mjModel` 但没有回滚**：一半参数改了、一半失败，仿真处于"半新半旧"状态。识别方法：**故意让一个参数越限，看是否其他参数也被改**。
- ❌ **辨识结果直接覆盖参数**：看起来很方便，但**丢掉了置信区间和实验条件**，下次没人知道这个数是怎么来的。识别方法：**看辨识值旁边有没有区间**。
- ❌ **度/弧度混用**：界面上显示度，存进去也是度，算法里当弧度用。识别方法：**设一个 90 的目标角，看机器人转多少**（这个 bug 在业界经典到有名字）。

## 4. 资产库选机器人（Asset Library / Robot Picker）

### (a) "完整实现"的段落定义

**完整实现 = 每一个资产都有可验证的来源、许可、自由度、限位、质量与内容哈希；能按条件检索（不是只有"5 台臂"的固定列表）；能预览（3D 静态/缓慢自转 + 关键元数据）；能导入 URDF/MJCF 并在导入时就报出单位、惯量、执行器类型的问题；能安全删除与恢复；导入的资产和内置资产在数据模型上完全同构。**

### (b) 功能拆解

**B1 元数据规范（现有 `模型/模型库.json` 已经是一个雏形，要升级）**

已具备：`标识 / 显示名 / 类别 / 目录 / 扭矩模型 / 可控制 / 自由度 / 执行器数 / 许可 / 模型文件`。

必须新增的字段：

| 新字段 | 为什么 |
|---|---|
| `来源`（URL + 上游 commit，`工具/模型清单.json` 已有 `menagerie_commit`，要接进每个资产） | 现在只在清单级，资产级没有 |
| `内容哈希`（每个模型文件 + 每个网格资产的 sha256） | 现有项目已有"逐文件哈希不变量"的纪律，资产层必须一致 |
| `关节限位` / `速度限位` / `力矩限位`（从模型读，权威值） | 规划（第 1 项）与参数表（第 3 项）都要，避免各处手敲 |
| `质量` / `质心` / `总惯量` | 导入校验与参数辨识的基准 |
| `网格统计`（顶点数、三角面数、GLB 体积） | 性能与分发体积管理 |
| `执行器类型`（力矩 / 位置 / 速度 / 组合） | 决定"可控制"的真实含义（现有 `可控制: nu==nv` 是必要不充分的） |
| `单位标度` / `单位来源`（导入时声明或推断，见 B3） | 单位错误是最常见的导入事故 |
| `标签`（臂型、DH 变体、是否带夹爪、是否带移动底盘…） | 搜索/筛选的前提 |
| `内置/导入` 标志 + `导入时间` | 治理：区分"随软件发布"与"用户自己加的" |
| `可用性`（可用 / 缺网格 / 缺许可 / 校验失败） | 让"能打开但显示不出来"的资产显式降级 |

**B2 资产注册表（单一事实来源）**

现状：`模型/模型库.json` 由 `工具/导入模型.py` 生成，是"索引"；`项目/*.json` 又各写一遍 `模型` 路径；界面再按项目反查。**三处可能不一致。**

规格要求：

- **一个** `资产注册表`（`资产/注册表.json` + 二进制缓存），是唯一权威
- 项目文件只存**资产 ID**（不是路径），资产移动/改名不破坏项目
- 启动时做**一致性自检**（沿用现有 `工具/验证/校验项目.py` 的思路）：项目引用的资产 ID 必须存在且校验通过，否则**启动即报警**（不是运行时才炸）
- `资产/` 目录布局：

```
资产/
  ├ 注册表.json               ← 唯一权威索引（含哈希）
  ├ 内置/                     ← 随软件发布，只读
  │   └ <资产ID>/ 原模型/ 预览.glb/ 元数据.json/ 许可.txt/ 来源.md
  └ 用户/                     ← 导入的，可写可删
      └ <资产ID>/ ...
```

（现有 `模型/` 108 MB 迁到这里；`归档/离线依赖/` 80 MB 不在资产库范围内。）

**B3 导入器（URDF / MJCF），含"导入即校验"**

现有 `工具/urdf_转_mjcf.py` + `工具/导入模型.py` 已有能力（menagerie 导入 + 生成 `*_torque.xml` 变体）。规格要求把它**从命令行工具升级为界面流程**，并补上校验层：

| 校验项 | 判定 | 严重度 |
|---|---|---|
| **单位推断** | URDF 里长度若不是米（整车/大臂常见 mm）；用包围盒尺度 + 质量合理性交叉验证 | **阻断**（问用户："这台臂长 1300，单位是 mm 还是 m？"）|
| 惯量合理性 | 三角不等式（`Ixx+Iyy ≥ Izz` 等）、非负、与质量×尺寸² 的量级一致性 | 警告 |
| 质量 | 总质量为 0 / 过大（>1000 kg 的小臂）/ 单连杆质量为负 | 警告或阻断 |
| 关节限位 | `lower < upper`、连续关节（`continuous`）处理、限位为 ±3.14 的默认值（意味着上游没填，快照"疑似未填"） | 警告 |
| 执行器 | 有/无 `<transmission>`；生成 `*_torque.xml` 是否成功；`nu` 与 `nv` 关系 | 报告 |
| 网格 | 缺文件、路径大小写、DAE/OBJ/STL 支持、体积超阈值 | 警告 |
| 碰撞几何 | 是否存在 `collision` 几何；是否与视觉几何一致 | 报告 |
| 基座固定 | 是否 free joint（悬空臂会掉下去） | 报告 |

**导入结果必须是一份"导入报告"**（可保存、可重新查看），而不是一句"导入成功"。**导入失败要能给上游提 issue 的信息**（哪个文件哪一行）。

**B4 预览**

- 静态/缓慢自转的 3D 预览（用 GLB 缩略件，不在预览里加载完整模型）
- 元数据卡：自由度、限位、质量、许可、来源、导入时间
- **"试跑"按钮**：用兜底控制器（关节空间正弦/PD）跑 3 s 并把结果缓存成小预览——这比纯静态预览有用得多，且成本低（复用第 2 项的渲染管线）
- 预览图生成（离线，导入时一次）：`预览.png`

**B5 浏览与检索**

- 搜索（名称、标识、标签）
- 筛选：自由度（2/6/7+）、执行器类型、许可类型（**商用友好 / 需注意**）、内置/用户、可用性、是否带夹爪、是否支持力矩控制
- 排序：名称、导入时间、体积、自由度
- 视图：卡片网格 / 表格（需要能看哈希与来源）
- **多选对比**：并排显示 2~3 台臂的关键参数（自由度、限位、质量、可达范围）——选型时真需要

**B6 删除 / 恢复 / 去重**

- 删除用户资产 → 进回收站（`资产/回收站/`），可恢复
- 内置资产不可删（可"隐藏"）
- **内容去重**：同一份网格被多个资产引用时只存一份（内容寻址）。现有 108 MB 里 UR5e/UR10e 共 62 MB，两台臂共享大量同源网格，去重收益可观。

**B7 治理（针对"参考项目 378 MB 无治理"的正面回应）**

参考项目的问题：资产原样进构建产物（`public/` 378 MB → `dist/` 424 MB）、无压缩/LOD/glTF 流水线、**无逐资产来源与许可元数据**、资产目录是代码（加机器人要改 TS 并重新构建）。

我们的要求：

| 治理项 | 验收标准 |
|---|---|
| 来源与许可 | **每个资产必须有** `来源.md` + `许可.txt`；缺失 → 注册表标 `可用性: 缺许可` 并在界面上可见 |
| 体积预算 | 内置资产**分发产物**（GLB + 元数据）总量目标 **≤ 40 MB**（源资产 108 MB 不入分发）；单个 GLB ≤ 8 MB（超则强制 LOD） |
| 流水线 | 源资产 → GLB（压缩 + LOD）→ 打包，**有版本化的脚本**，不是手工操作 |
| 声明式 | 加一台机器人 = **放文件 + 跑一次注册**，不改任何代码（针对"资产目录是代码"的反面） |
| 校验 | 注册表自检纳入现有断言集（当前 514 项 / 6 套） |

### (c) 数据/状态模型

```
资产 Asset
  ├ id (稳定标识) / 显示名(中英) / 类别
  ├ 路径: {原模型, 扭矩变体, 预览GLB, 预览PNG, 元数据, 许可, 来源}
  ├ 物理: {自由度, 执行器数, 关节限位[n], 速度限位[n], 力矩限位[n],
  │        质量, 质心, 总惯量, 基座是否固定}
  ├ 控制: {执行器类型, 可控制(nu==nv), 支持力矩接口}
  ├ 几何: {网格数, 总顶点, 总三角面, GLB体积, LOD级别}
  ├ 来源: {类型(内置/用户), URL, 上游commit, 导入时间, 导入器版本}
  ├ 许可: {标识, 文件路径, 商用友好}
  ├ 可用性: {状态, 原因}
  ├ 标签[]
  └ 哈希: {文件 → sha256}

注册表 Registry  { schema版本, 资产[], 生成时间, 自检结果 }
导入报告 ImportReport { 源文件, 逐项校验结果, 阻断项, 警告项, 生成物清单 }
```

**风险**

1. **URDF→MJCF 的兼容面**：现有 `工具/urdf_转_mjcf.py` 能转，但真实世界的 URDF 千奇百怪（xacro 展开、package:// 路径、mesh scale、mimic joint、连续关节）。**"导入任意 URDF"是一个无底洞**：建议明确划定支持面（" Mujoco 能直接加载的 MJCF/URDF"），并把不支持的情况做成**清晰的失败报告**而不是崩溃。**这是本项最容易被低估的地方。**

### (e) "假但像样"会是什么样

- ❌ **硬编码资产目录**（现有 `模型库.json` 的形态）：加机器人要改代码/重新生成索引，且索引与项目文件可能不一致。识别方法：**手动往资产目录放一个模型，看它是否自动出现**。
- ❌ **导入时只做"能不能加载"，不做校验**：单位是 mm 的 URDF 也能导入，机器人小得像蚂蚁或大得像楼。识别方法：**导入一个 mm 单位的模型**。
- ❌ **许可字段是"Apache-2.0"的硬编码字符串**：所有资产都写同一个值。识别方法：**看每个资产的 `许可.txt` 是否存在且各不相同**。
- ❌ **预览是静态占位图**：所有机器人显示同一张图。识别方法：**并排看 5 个资产的预览**。
- ❌ **无哈希**：资产被静默替换/损坏无法发现。识别方法：**改一个字节再打开**。

## 5. 诊断（Diagnose）

### (a) "完整实现"的段落定义

**完整实现 = 诊断页里的每一个数字都来自真实的采集点（有明确的采样率、缓冲深度、时间戳与来源），没有硬件或物理模型支撑的量就不显示；系统能从这些时序数据里自动检出几类确定的病态（振荡、抖动、饱和、发散、跟踪超差、模型失配），每一条结论都能给出发病时段、量化证据和一条可执行建议，并支持一键跳到该时段、导出报告、把该时段存为记录以便复现。**

### (b) 功能拆解

**B1 全速采集层（"不扰动仿真"是硬要求）**

- **仿真侧以物理步进频率（500~1000 Hz）把通道写入环形缓冲**，不做任何分配、不加锁（单写者单读者）、不格式化字符串
- 通道清单（这是"真诊断"与"假诊断"的分界线）：

| 分组 | 通道 | 来源 | 备注 |
|---|---|---|---|
| 跟踪 | 每关节 `q - q_des`、`qd - qd_des` | `mjData` + 控制器内部目标 | 目标必须由控制器真提供，不能事后插值编造 |
| 力矩 | 每关节指令力矩、实际广义力 `qfrc_actuator`、重力/科氏项 `qfrc_bias` | `mjData` | |
| 饱和 | 每执行器 `abs(ctrl) / ctrlrange_max`、饱和计数与累计时长 | `mjModel.actuator_ctrlrange` | 饱和是一个**计数统计**，不是瞬时值 |
| 限值 | 每关节速度/加速度与上限之比、**jerk 估计** | 数值微分 + 限位 | jerk 必须滤波，否则全是噪声 |
| 接触 | 接触数 `ncon`、逐接触力大小/法向/切向、最大接触力、滑移速度 | `data.contact` + `mj_contactForce` | |
| 约束 | `nefc`、约束违反量、`mjData.solver_niter`（**本机实测可取**） | `mjData` | 求解器迭代数是真量 |
| 时序 | `mj_step` 耗时、控制律耗时、每轮总耗时、实际步进频率、**实时因子 RTF** | 计时器 | |
| 队列 | 各消息通道队列深度、丢弃数、最坏延迟 | 传输层 | 对接第 7 项 |
| 记录 | 录制写入耗时、丢帧数 | 录制层 | 100 Hz 录制是否掉点 |

- **两个采样率**：物理频率全量进环形缓冲（默认 60 s @ 1 kHz）；按**抽取**送到界面（界面最多 30 Hz，曲线按 min/max 抽取以免丢尖峰——**只做均值抽取会掩盖抖动，这是常见错误**）
- 内存预算：50 通道 × 60 000 样本 × 8 B ≈ 24 MB，可接受；环形缓冲可扩到 10 分钟（约 240 MB）作为可选

**B2 手动诊断视图（人看的）**

- 多 Y 轴时序曲线（每关节一行小图 + 叠加对比），共用时间光标
- 实时值表（当前值 / 峰值 / 均值 / RMS / 标准差 / 越限计数）
- 频域视图（FFT / 频谱图）——**这是"振荡检测"的证据形式**，不是装饰：机械臂抖动在频域一眼可见，时域要靠猜
- 相图（`q` vs `q̇`）用于观察极限环（自激振荡）
- 触发力矩/接触力随时段的热力条

**B3 自动检测器（这是"诊断"的核心价值，必须有，否则只是示波器）**

每个检测器有：输入通道、判据、阈值（默认值 + 可调）、输出结构 `{类型, 严重度, 时段, 证据, 建议}`。

| 检测器 | 判据（可实现的） | 建议动作 |
|---|---|---|
| **振荡** | 速度信号的 FFT 在 5~200 Hz 有显著峰，且峰值功率占比 > 阈值，且持续 > 0.5 s | 降 KP / 加 KD / 降采样周期抖动检查 |
| **抖动/颤振（chattering）** | 指令力矩的符号变化率（零穿越次数/秒）> 阈值 | KD 偏大或时间步与刚度不匹配 |
| **饱和** | `abs(ctrl)/limit > 0.98` 的时间占比 > 阈值 | 力矩上限不足 / 目标不可达 / 增益过大 |
| **发散** | `abs(q)` 或误差包络指数增长（对数斜率 > 0） | 控制器不稳定，立即停（联锁） |
| **跟踪超差** | `abs(误差)` 超过项目设定容差持续 > T | 前馈缺失 / 增益不足 / 模型失配 |
| **模型失配** | 实测力矩与模型预测力矩（`M q̈ + C q̇ + g`）的残差超阈值；或辨识残差超阈值 | 重新辨识 / 检查质量与质心 |
| **约束打架** | `nefc` 异常高或 `solver_niter` 顶到 `opt.iterations` | 提高迭代次数 / 检查几何穿插 |
| **步进超期** | 单步耗时 p99 > 步进周期的 50% | 降低控制频率 / 简化模型 |
| **数值异常** | 出现 NaN/Inf、`qacc` 爆炸 | 立即停 + 报出首次出现的通道与时刻 |
| **失稳（能量）** | 系统总能量（`mj_energyPos + mj_energyVel`）在没有输入时增长 | 积分器/阻尼问题 |

**B4 结论卡片与可操作性（"用户拿它做什么"）**

每条结论是一张卡片：`严重度图标 + 一句话 + 时段 + 证据（可展开的曲线缩略图）+ 建议 + 三个动作`。

三个动作必须是：**① 跳到该时段**（曲线与 3D 联动定位），**② 存为记录**（把该时段的原始数据 + 当时参数 + 模型 hash 打包，供复现），**③ 导出**（Markdown/HTML 报告，含图）。

**严重度分级与联锁**：`信息 / 警告 / 严重 / 致命`。**"致命"（发散、NaN）可以触发自动暂停**（可配置），这是唯一一处诊断会影响控制的路径，必须显式可关。

**B5 与参数辨识、录制的接口**

- 辨识残差曲线（第 3 项 E 类）作为"模型失配"检测器的输入之一
- 诊断结论可以**直接触发一次录制**（"从此刻开始录 10 秒"）
- 诊断时段与录制文件用相同的仿真时间轴，保证能对上

**B6 什么不该出现在诊断里（防止把"假"做出来）**

| 不做的量 | 原因 |
|---|---|
| **电机温度** | 无热模型、无硬件。**不显示，或明确标注"需真实硬件遥测"**。参考实现的 Diagnose 用假力矩公式（LE 报告 §0），绝不重复 |
| 电流 | 无电机模型。若做，必须由力矩与 `电机常数`（辨识得到的参数）**换算并标注"估算"**，且要显示所用常数来源 |
| 关节磨损/寿命 | 无模型 |
| "健康分" | 单一数字无法诊断。**不做总评分**（那是给人看的，不是给工程师看的） |
| 延迟/抖动 | 除非真的测了（第 7 项），否则不显示 |

### (c) 数据/状态模型


**风险**

1. **检测器的误报/漏报**是本项最大的工程风险（不是技术风险）。对策：**每个检测器必须有一个"已知病态"的构造用例**（人为把 KP 调爆 → 必须报振荡；把力矩限位压到 1 N·m → 必须报饱和；给一个错误质量 → 必须报模型失配）。**没有构造用例的检测器不许上线**——否则它会变成一个天天响的闹钟，用户三天后就关掉它。
2. **jerk 与加速度是数值微分的产物**，噪声极大。必须实现滤波器（Butterworth 或滑动多项式）并把**滤波器参数显示给用户**。这一条不做，"抖动检测"就是噪声检测。
3. **全速采集的开销**：50 通道 × 1 kHz 在 Python 里如果逐通道逐样本赋值，会成为热点。对策：用 `numpy` 预分配数组 + 切片整体写入；**必须先做一次开销实测**，如果单步开销增加 > 5%，降到 500 Hz 采集或降通道数。

**风险预算：+7 人日 → 区间 51~58 人日。**

### (e) "假但像样"会是什么样

- ❌ **用 `sin(t)` 生成"力矩曲线"**（参考实现的原罪）。识别方法：**把机器人静止冻结，看曲线是否变成一条直线**——假数据会继续波动。
- ❌ **显示"电机温度 45 °C"**。识别方法：**问它是怎么算出来的**。
- ❌ **只有一个"健康度 92 分"**。识别方法：**点它，看能不能定位到时段与通道**。
- ❌ **图表是漂亮但无时间戳的快照**：无法与仿真时间、录制、日志对齐。
- ❌ **检测器永远不报**（阈值设成永不触发）或**永远在报**（阈值太敏感）。识别方法：**做 6 个构造病态用例**。
- ❌ **诊断曲线用均值抽取**：尖峰被抹平，"看起来很正常"。识别方法：**人为注入一个单步尖峰，看能否在曲线上看到**。

## 6. 部署（Deploy）

### (a) "完整实现"的段落定义

**这一项的"完整"必须是分阶段的**，因为它一半依赖硬件（还不存在）。诚实定义：

**完整实现（阶段 1~3，无硬件也能做完）= 一套与硬件无关的设备抽象（含完整语义：模式机、命令/状态、时间戳、状态机、错误码），一个模拟后端（在仿真里当硬件用，含可注入的延迟/丢包/抖动/量化），一套在任何后端都生效的安全层（看门狗、限幅、限速、心跳、安全状态、审计日志），一条"仿真 → 带延迟仿真 → 硬件在环 → 真机"的四级推进路线与每级的准入条件，以及一个能让第三方写驱动的接口契约 + 契约测试。**

**完整实现（阶段 4，需要硬件）= 至少一个真实协议后端（推荐先做 UDP/CAN 这类低门槛的），在真机上跑通过一条规划轨迹，并通过全部安全验收项。**

### (b) 功能拆解

**B1 抽象边界（"诚实且可扩展"的具体形态）**

三层，每层职责唯一：

```
① 控制器层（算法）：算法库/通用/轨迹跟踪.py 等
      ↓ 只产出「期望关节位置/速度/力矩」——不知道硬件存在
② 设备抽象层 DeviceBackend（协议无关）
      ↓ 状态机 / 限幅 / 看门狗 / 时间戳 都在这一层之上（不在协议层里）
③ 传输层 Transport（协议相关）：Sim | UDP | CAN | EtherCAT | ROS2 | 串口 | 厂商SDK
```

**设备抽象必须是"同步写、异步读"的语义**，并且**时间戳是接口的一部分**（不是可选的）：没有时间戳就没法做实时性诊断（第 7 项）也没法做安全检查（"这条状态是 200 ms 前的"）。

```python
class 设备后端(Protocol):
    名称: str; 版本: str
    自由度: int                          # 从模型来，不写死 6
    能力: 设备能力                        # {可读位置, 可读速度, 可读力矩, 可读电流, 可读温度, 支持力矩模式, ...}
    def 打开(self, 配置) -> None: ...
    def 关闭(self) -> None: ...
    def 设模式(self, 模式: 控制模式) -> None: ...   # 位置/速度/力矩/空闲/急停
    def 写命令(self, 命令: 命令帧) -> 写结果: ...   # 非阻塞；携带 seq 与 期望生效时刻
    def 读状态(self) -> 状态帧: ...                # 非阻塞；携带 采集时刻 + 接收时刻 + seq
    def 健康(self) -> 健康报告: ...
```

**能力声明必须被真正使用**：控制器在"只能力矩模式"和"只能位置模式"的硬件上要走不同的代码路径。**"能力声明了但不读"= 假抽象**（识别方法见 (e)）。

**B2 协议/传输候选（现实清单与排序）**

| 协议 | 现实性 | 何时选 | 工作量（含调试） | 诚实评价 |
|---|---|---|---|---|
| **UDP（自定义轻协议）** | ★★★★★ | 第一台原型硬件 / 自制关节模组 / 单片机 | **5~8 人日** | 最诚实的第一步。无实时保证，但能验证整条链路。含 seq/时间戳/丢包统计即可 |
| **串口 / USB-CDC** | ★★★★★ | 单轴或少数轴的模组、调试 | **3~5 人日** | 最简单，带宽最低。适合先跑通一台单关节模组 |
| **CAN / CAN-FD** | ★★★★ | 关节模组总线（很多国产模组用 CANopen/CAN-FD 私有协议） | **15~25 人日** | macOS 上需要 USB-CAN 适配器 + python-can；协议细节（PDO 映射、心跳、SDO）是主要成本 |
| **ROS 2** | ★★★ | 已有 ROS 2 机器人，或要用 MoveIt | **25~40 人日** | **与"纯 Python 单进程桌面软件"的现状冲突**（LE 报告已指出）。若走这条路，本质是把部署外包给 ROS 生态。不建议第一步就上 |
| **EtherCAT** | ★★ | 工业机械臂/伺服，有厂商栈 | **40~80+ 人日** | **macOS 基本不可行**（需要实时内核 + IgH/TwinCAT/厂商栈）。要做得换 Linux + PREEMPT_RT。**这是"月"级的活，不是"周"** |
| **厂商 SDK**（UR RTDE / Franka FCI / xArm SDK） | ★★★ | 手上确实有该品牌机器 | **10~20 人日/品牌** | **最现实的"真机第一跑"路径**：UR 的 RTDE 是标准 Ethernet + 500 Hz 状态流，非常适合本项目；Franka FCI 是 1 kHz。但每家一个后端，且许可/安全认证各不相同 |

**排序建议（明确）**：`UDP/串口 → 厂商 SDK（若有实物）→ CAN → ROS 2 → EtherCAT`。

**B3 安全故事（必须先是"绝不允许"清单，再是实现）**

**绝不允许依赖上位机流式指令才能安全**（即：上位机崩了、网断了、软件被 kill 了，硬件必须自己进入安全状态）：

1. **看门狗在硬件/驱动侧**：命令带心跳计数与超时时间（如 20 ms）。**超时 → 硬件本地进入阻尼/断电抱闸**。不能是"上位机发现超时再发停止指令"——那时上位机已经死了。
2. **限位在驱动/固件侧**：关节软限位、速度限位、力矩限位必须在**下层**也有一份。上位机的限幅是"第二道"不是"唯一一道"。
3. **急停是物理回路**：软件按钮是"请求"，**必须另有物理急停回路**（硬件使能线断开）。规格明确写：软件不承担人身安全职责。
4. **上电/使能的状态机**：`未连接 → 已连接(未使能) → 使能中 → 运行 → 停止 → 故障 → 急停`。**不允许跳过"未使能"直接运行**；每次进入"运行"必须由用户显式确认（不能记忆上次状态自动恢复运行）。
5. **首帧保护**：使能后的第一条命令必须是"当前位置保持"（读到的当前姿态），**不允许**第一条就跳到某个目标（经典事故：上电瞬间满速冲目标）。
6. **限速渐变**：目标位置/速度的**变化率**受限（Clipping + rate limiter），位置指令要做**增量限幅**（单周期最大位移）。
7. **审计日志**：每一次模式切换、每一条被限幅/被拒绝的命令都记日志（含时间戳、原因），可导出。这是事后复盘的唯一依据。
8. **禁用高风险自动化**：不允许"规划完成后自动开始执行真机动作"——必须由人按下执行。

**B4 四级推进路线（每级有准入条件）**

| 级 | 名称 | 做什么 | 准入条件（进入下一级） |
|---|---|---|---|
| **L1** | 纯仿真 | 现有能力；部署后端 = `SimBackend` | 规划轨迹在仿真里跟踪误差达标 |
| **L2** | 带延迟仿真 | `SimBackend` + 可注入延迟（1/2/5/10 ms）、抖动、丢包、量化（编码器分辨率）、单步保持 | 在 5 ms 延迟 + 1% 丢包下仍稳定（不振荡、不发散）；看门狗演练能触发 |
| **L3** | 硬件在环（HIL） | 真控制器（真硬件或真固件的仿真）+ 我们的软件；或我们的软件 + 硬件在环的电机模型 | 通信链路连续 30 分钟无丢包；时间戳诊断通过；急停演练通过 |
| **L4** | 真机 | 真实机械臂 | 全部安全验收项通过 + 有人在急停旁边 |

**L2 是"无硬件也能做的最有价值的事"**，它能把大部分控制器对延迟的敏感性在仿真里暴露出来。**规格要求 L2 必须实现**：`SimBackend` 的延迟/丢包/量化注入是**接口级**的（不是加个 `sleep`），可复现（固定随机种子）。

**B5 无硬件时能诚实交付的东西**

- `设备抽象` 接口 + 契约测试（**用契约测试验证任何后端**：延迟统计、时间戳单调性、能力声明与行为一致、错误码覆盖）
- `SimBackend`（含 L2 的劣化注入）
- `UDP` 与 `串口` 后端 + 一个**协议模拟器**（脚本扮演硬件，回复状态帧）——这让整条链路（含超时、重连、错误处理）在没硬件时就能真跑
- 安全层全部（看门狗、限位、状态机、审计、首帧保护）
- 部署 UI（连接配置、状态机可视化、实时遥测、命令日志、演练按钮）
- **明确的"未验证"标注**：界面上任何来自真实硬件的量，在没有硬件时**必须显示"未接入"而不是 0**

### (e) "假但像样"会是什么样

- ❌ **Deploy 页面全是 mock 数据**（参考实现就是这个："Deploy 整模块"都是 mock，健康检查 `ok` 硬编码为真）。识别方法：**看它有没有"未接入"状态**——假实现永远显示"已连接"。
- ❌ **抽象层只有一个实现**（`SimBackend`），接口是照着仿真写的，真协议接不进来。识别方法：**看接口里有没有时间戳、seq、能力声明、错误码**。
- ❌ **安全靠上位机发停止指令**：看起来有"急停"按钮，实际硬件不自己看门狗。识别方法：**kill 掉上位机进程，看硬件是否停**。
- ❌ **"支持 EtherCAT"写在功能表里但没有一个后端**。识别方法：**问用的是哪个主站栈、在什么平台上**。
- ❌ **延迟数字是算出来的不是测出来的**。识别方法：**看有没有 p99 和实测记录，以及时间戳是采集时刻还是接收时刻**。

## 7. 系统监控（SystemMonitor）

### (a) "完整实现"的段落定义

**完整实现 = 每一条曲线都对应一个真实的计数器或计时器，采集本身的开销被测量并公开（"监控占用 X% 的单步时间"），能回答"为什么实时因子掉到 0.83"这种具体问题（逐阶段分解：物理、控制、采集、传输、渲染、录制），有阈值与告警（含静默与去抖），并且在高负载下自己能降级而不是把系统拖垮。**

### (b) 功能拆解

**B1 哪些指标才真的重要（本项的"选品"决定它有用还是没用）**

排序原则：**能直接解释"仿真跑不快/不稳"的指标优先**。

| 优先级 | 指标 | 采集方式 | 为什么重要 |
|---|---|---|---|
| **P0** | **逐阶段耗时**：`mj_step`、控制律、采集、编码/传输、录制写入 | 每轮 `perf_counter` 差值，环形缓冲 | **这是唯一能回答"时间花在哪"的指标**。只看总 RTF 等于什么都没说 |
| **P0** | **物理步进频率与抖动**（实际 Hz、周期 p50/p99/max） | 时间戳差分 | macOS 上 `sleep` 过冲是已知问题（100 Hz 实测只有 83.8 Hz），抖动必须可见 |
| **P0** | **实时因子 RTF**（仿真时间 / 墙钟时间） | 累积比对 | 产品级第一指标（现有实测 0.86×） |
| **P0** | **消息队列深度 / 丢弃数 / 最坏延迟**（每通道） | 传输层计数 | 队列积压是"界面越来越卡"的根因 |
| **P1** | **UI 帧时间 p50/p99 + 丢帧数** | 前端 `requestAnimationFrame` 直方图 | 前端卡顿与仿真卡顿是两件事，必须分开看 |
| **P1** | **内存**：进程 RSS、Python 对象数、numpy 缓冲占用 | `psutil` / 自计 | 长时间运行泄漏（录制缓冲、曲线历史是常见泄漏源） |
| **P1** | **线程健康**：每线程心跳时间戳、是否卡住、是否退出、GIL 争用迹象 | 线程内打点 | "仿真线程死了但界面还在动"是最糟的故障，必须能立刻看出 |
| **P1** | **插件错误计数**（沿用现有 `出错插件()` / `停用插件()` 语义）与**每插件耗时** | 现有安全注册表 | 已具备基础设施，接出来即可 |
| **P2** | 磁盘：录制写入速率、剩余空间 | OS 调用 | 长录制会写满盘 |
| **P2** | CPU 占用（总/单核饱和） | OS 调用 | 与"是否还有余量"相关 |
| **P2** | 网络带宽（姿态流/曲线流） | 传输层字节计数 | 远程访问时重要 |
| **P3** | GPU / 显存 | **浏览器侧不可靠，不做** | 宁可缺，不要假 |

**B2 采集方式（"不扰动仿真"的具体机制）**

四类采集，代价递增，规格要求逐类实测开销：

1. **计数器**（队列深度、丢弃数、插件异常数）：无锁自增，代价 ~ns
2. **计时器**：每轮 4~6 次 `perf_counter()`（每次约 20~50 ns，可忽略）；**不用 `time.time()`**（墙钟会跳）
3. **内存/线程**：**低频采样（1 Hz）+ 独立线程**，绝不在仿真循环里调 OS
4. **UI 帧时间**：前端测，不回传原始数据，只传直方图

**开销公开（这是本项诚实性的核心）**：监控页顶部**必须显示**"监控采集占单步时间 X%"（用一个可开关的 A/B 实测得出：关掉采集跑 5 s，打开跑 5 s，对比步频）。**如果 X > 3%，采集层必须降级**（降采样到 1/10）。

**B3 阈值与告警**

| 指标 | 警告 | 严重 | 动作 |
|---|---|---|---|
| RTF | < 0.95 | < 0.8 | 提示（并附带逐阶段分解，指出瓶颈阶段） |
| 步进周期 p99 | > 周期 × 1.5 | > × 3 | 提示 |
| 队列深度 | > 容量 50% | > 80% | 自动降采样曲线推送 |
| 丢弃数 | 10 s 内 > 0 | 持续丢 | 提示 |
| UI 帧时间 p99 | > 33 ms | > 50 ms | 触发 3D 降级（第 2 项 B9） |
| RSS | > 2 GB | > 4 GB | 提示（附最大缓冲占用者） |
| 线程心跳 | 超期 1 s | 超期 3 s | **严重**（可能是死锁） |
| 插件异常 | 单插件 10 s 内 > 5 次 | 已被停用 | 严重 + 指向插件面板 |

**告警必须有去抖与静默**：同一告警 30 s 内不重复弹；用户可"静默 10 分钟"（**但状态栏图标保留**，见第 9 项）。**没有去抖的告警系统一定被关掉。**

**B4 显示**

- 顶部**一屏摘要**：RTF、步频、UI fps、队列最大深度、告警数（5 秒内能看懂）
- **阶段耗时堆叠图**（时间轴上是各阶段的堆叠面积）——一眼看出谁在变胖
- 曲线网格（可选的指标加入自定义面板）
- **线程心跳表**（线程名 / 最后心跳 / 状态 / 累计轮数）
- **自监控**：采集开销、监控面板自身的 CPU 占用
- 导出：诊断报告（第 5 项）里可嵌入监控快照

**风险**

1. **计时本身的噪声**：`perf_counter` 在子微秒级别不稳定，`mj_step` 只有 3.39 µs（本机实测），单步计时会被噪声淹没。对策：**测批量（例如每 100 步累计一次再平均）**，并把统计窗口显示出来。这一条不注意，"物理耗时"曲线会是一条毛刺。
2. **监控侵入性**：任何在仿真循环里的采集都是风险。规格的硬性要求是**仿真循环里只有加法和数组切片**，任何字符串格式化、字典构造、JSON 序列化都在**另一个线程**做。这一条破坏起来很容易（一句 `f"{...}"` 就够了）。
3. **告警风暴**：一次卡顿会同时触发 5 条告警。对策：告警按"根因"归并（RTF 掉了就不要再单独报"步频掉了"）。

**风险预算：+4 人日 → 区间 33~37 人日。**

### (e) "假但像样"会是什么样

- ❌ **用随机数或 `sin` 生成 CPU/内存曲线**。识别方法：**开一个死循环线程，看 CPU 曲线是否真的上去**。
- ❌ **只有总体 CPU 和内存，没有逐阶段分解**：好看但回答不了任何问题。识别方法：**问"这 0.83 的 RTF 是谁吃掉的"，看能不能答**。
- ❌ **队列深度永远是 0**（因为根本没统计，或者统计的是另一个队列）。识别方法：**故意让消费端慢下来，看数字是否增长**。
- ❌ **线程心跳是"线程对象还活着"**：线程可以在死循环里"活着"。识别方法：**让线程卡在一个长 `sleep` 里，看心跳是否停**。
- ❌ **监控自身开销不测不报**。识别方法：**看有没有"监控占用 X%"这一行**。

## 8. 插件市场（Plugin Marketplace）

### (a) "完整实现"的段落定义

**完整实现 = 第三方控制算法有一条完整的、每一步都有证据的生命周期：清单声明 → 索引发现 → 下载 → 校验（哈希/签名）→ 静态检查（API 版本、依赖、模型兼容性、危险调用）→ 用户显式授权 → 安装到用户目录 → 运行（在沙箱边界内，或明确告知无沙箱）→ 出错隔离（沿用现有机制）→ 升级/降级 → 卸载（不留残留）。并且有一套本地开发流程（模板、热重载、本地打包、自检工具），让"写一个插件"仍然像现在一样是"新建一个文件"。**

**必须先说清的一条**：**这是任意 Python 代码。在进程内运行的 Python 无法被真正沙箱化。** 任何声称"我们的插件市场是安全的"的说法都是假的。规格的态度是：**用工程手段把风险变成"可见的选择"，而不是假装风险不存在**（详见 B4）。

### (b) 功能拆解

**B1 清单格式（Manifest）**

现有插件用**类属性**声明元信息（`名称/版本/说明/作者/英文名/接管控制`）+ 独立的 `项目/*.json` 声明装配。清单要**扩展**而不是替换：

```jsonc
{
  "schema": "yubi.plugin/1",
  "id": "com.example.joint-pd",          // 反向域名，全局唯一，安装后不改
  "name": { "zh": "关节 PD 位置控制", "en": "Joint PD position control" },
  "version": "1.2.0",                     // SemVer
  "api_version": "1.x",                   // 宿主接口契约版本（现有 骨架/官方接口清单.py 的插件侧对应物）
  "entry": "关节pd控制.py",                // 模块文件
  "class": "关节PD控制插件",               // 可省：模块内唯一插件类时自动识别（沿用现有约定）
  "kind": "controller",                   // controller | recorder | identifier | metric | viewer
  "takes_control": true,                  // = 现有 接管控制
  "description": { "zh": "...", "en": "..." },
  "authors": ["..."],
  "license": "MIT",
  "homepage": "https://...",
  "requires": {
    "python": ">=3.10,<3.12",
    "packages": [ {"name": "numpy", "spec": ">=2.0"} ],     // 只允许声明，安装时校验
    "yubi": ">=0.9"
  },
  "robots": {                              // 兼容性声明（不再靠运行时抛异常发现）
    "dof": [6, 7],                         // ★ 或者是 "any"
    "requires": ["nu==nv", "torque_actuators"],
    "excludes": []
  },
  "parameters": [                          // 与第 3 项的参数表对接
    { "key": "KP", "type": "float", "default": 200.0, "unit": "N·m/rad",
      "range": [0, 10000], "label": {"zh": "比例增益", "en": "Proportional gain"} }
  ],
  "metrics": [ {"key": "跟踪误差(mm)", "unit": "mm"} ],
  "safety": { "writes_ctrl": true, "realtime": true },   // 声明是否在热路径写控制量
  "integrity": { "files": { "关节pd控制.py": "sha256:..." } }
}
```

**关键设计决定**：清单是**声明**，代码里已有的类属性**仍是权威运行时来源**；两者不一致时**启动时的自检要报出来**（这是"清单漂移"的唯一防线）。

**B2 索引与分发（现实方案）**

| 方案 | 评价 | 建议 |
|---|---|---|
| **Git 仓库 + 静态索引 JSON** | 可审计（每个版本一个 commit）、无需服务端、天然支持离线镜像 | ✅ **首选**。索引 = 仓库里的 `index.json`，条目指向 `releases/<id>/<version>/` |
| 静态文件服务器（CDN） | 快，但要额外的发布流程 | ✅ 作为镜像（索引里可写多个源 URL） |
| 自建服务端 API | 需要运维、鉴权、数据库 | ❌ 现在不做（参考项目的"约 60 行 FastAPI 就够了"说明服务端不值钱，但运维值钱） |
| PyPI 式 | 生态成熟但语义不匹配（插件不是包） | ❌ |

**索引条目**：`{id, version, 下载URL, 大小, sha256, 签名, api_version, 最低宿主版本, 发布日期, 下载量?, 声明摘要}`。

**离线优先**（本项目的既有传统：`归档/离线依赖/` 支持无网安装）：安装器必须支持**从本地文件/目录安装**（`.yubi-plugin` = 一个 zip，内含清单 + 代码 + 可选签名），并且**索引可以缓存**（缓存里带签名，过期只提示不阻断）。

**B3 版本与兼容性**

- **插件版本** SemVer；**宿主接口契约版本**独立（`api_version`）。
- 兼容性判定**四条**（全部在安装时做，不等到运行）：
  1. `api_version` 与宿主是否兼容（现在是 `1.x`；破坏性变更升主版本）
  2. 依赖的 Python 包是否满足（**只检测不自动装**——自动 `pip install` 是安全与稳定性的双重风险；缺失就明确告知命令）
  3. 机器人兼容性：`dof` 列表 vs 当前模型；`requires` 的机器能力（`nu==nv`、扭矩执行器）用 `mjModel` 实测校验——**这正是现有 `模型兼容性()` 钩子在做的事，把它提前到安装时**
  4. 参数 schema 是否与宿主参数表兼容

- **同一插件的多版本共存**：允许，安装时写入 `<id>@<version>/`；项目文件里可以指定版本（现有 `{"插件": "名字"}` 扩展为可选 `"版本"`）。**默认用最新兼容版**。

**B4 信任边界（必须诚实）**

**分级（三档），每一档的界面文案不同**：

| 档 | 来源 | 校验 | 运行时 | 界面文案 |
|---|---|---|---|---|
| **T1 内置/官方** | 随软件发布，走代码审查 | 哈希 | **进程内** | "官方算法" |
| **T2 索引签名** | 从索引安装，签名验证通过 | 哈希 + 签名（**规定：Ed25519 签名，公钥内置**） | **进程内**（默认） | "来自索引（已签名），可访问你的文件和仿真数据" |
| **T3 手工侧载** | 用户从本地文件安装 | 只算哈希，显示给用户 | **进程内** | **"⚠ 未验证的第三方代码，将以你的用户权限运行，可读写你的文件"** + 必须手动勾选确认 |

**诚实的话必须写在界面上（不是文档里）**：

> 本软件的控制算法以 Python 插件形式在仿真进程内运行。Python 插件**无法被真正沙箱化**——一个恶意插件可以读写你的文件、发起网络请求、崩溃软件。安装插件前请确认来源可信。我们从索引安装的插件会验证签名，但这只证明"来源"，不证明"安全"。

**可选的进程隔离（明确为"限制，不是沙箱"）**：为高风险插件提供"**独立进程 + 受限 IPC**"模式（插件只能通过一个消息接口收发控制量，不能 import 宿主内部模块）。代价：控制周期增加一次 IPC（**必须实测：在 1 kHz 下是否可行**），且延迟/抖动会进入控制回路。**建议：先做接口层的"最小权限 API"**（插件只能拿到 `mjModel`/`mjData` 的只读视图 + 写 `ctrl` 的权限），**进程隔离列为可选、默认关**。

**静态检查（不是沙箱，是"提示"）**：安装时扫描危险调用（`os.system`、`subprocess`、`socket`、`eval/exec`、`ctypes`、写文件路径），**在界面上列出"该插件将做以下事情"**。误报可接受（用户可跳过），漏报不可怕（因为它本来就不是沙箱）——**但不要把它宣传成安全机制**。

**B5 本地开发流程（"写一个插件仍然像新建一个文件"）**

现有流程已经很轻（复制模板 → 改类名 → 在项目 JSON 里加名字）。规格要求**不增加负担**，反而加三个工具：

1. **模板生成器**：`新建插件 → 填 id/名字 → 生成 <id>/ 目录 + 清单 + 代码骨架`（一键，含清单校验）
2. **热重载**：开发模式下改插件文件 → 自动重新装配该插件（**不重启软件**；其他插件与仿真状态不受影响）。这是开发体验的关键，且现有装配器已是"重新装配整组算法"的模式，热重载是它的自然延伸。
3. **本地校验工具**：`校验插件.py`（纳入现有 `工具/验证/` 家族）：
   - 清单 schema 校验
   - 与代码类属性一致性（漂移检测）
   - 声明的能力 vs 实际行为（`takes_control=true` 但从不写 `ctrl` → 警告，**这正是现有 `接管控制` 声明要解决的"静默被掩盖"问题**）
   - 危险调用扫描
   - 参数 schema 与 `可调参数()` 的一致性
   - 在 2/6/7 轴模型上的加载测试（不需要真的跑控制）

**B6 安装/升级/卸载的工程细节**

- 安装位置：`插件/<id>@<version>/`（**用户目录**，与内置的 `算法库/通用/` 区分）
- 原子安装：先解压到临时目录 → 校验哈希 → 原子改名（**不允许半装状态**）
- 卸载：删目录 + 清理缓存 + 从项目文件里移除引用（**要提示"有 N 个项目引用了它"**）
- 升级：保留旧版本（可回滚），默认只保留最近 2 个版本
- **证据**：每次安装/卸载写审计日志（时间、来源 URL、哈希、签名者）
- 与现有项目机制的整合：插件的"加入/移出项目"仍是 `项目/*.json` 的 `算法` 列表，插件市场只是让"插件从哪来"这一步有治理

### (c) 数据/状态模型

```
插件清单 Manifest（见 B1，落盘为 plugin.json）
索引 Index { schema版本, 生成时间, 条目[] }
索引条目 IndexEntry { id, version, url, size, sha256, 签名, api_version, min_host, 发布日期, 摘要 }
已装插件 InstalledPlugin { id, version, 安装路径, 来源(T1/T2/T3), 哈希, 签名者?, 安装时间, 状态(启用/禁用/错误), 审计引用 }
兼容性报告 CompatReport { api_ok, 依赖缺失[], 机器人要求[], 参数schema_ok, 危险调用[], 类属性漂移[] }
授权记录 Consent { 插件id, 版本, 用户确认时间, 文案版本 }   ← 政策变更要重新征求同意
```

### (d) 工作量与风险

| 工作包 | 人日 |
|---|---|
| B1 清单 schema + 与现有类属性的兼容层 + 漂移检测 | 5 |
| B2 索引工具（生成/校验/签名）+ 本地安装包格式 | 5 |
| B3 兼容性四判 + 多版本共存 + 项目引用扩展 | 6 |
| B4 三级信任 + 签名验证 + 授权 UI（含诚实文案）+ 危险调用扫描 | 6 |
| B4 最小权限 API（只读模型视图 + 写 ctrl 权限） | 5 |
| B5 模板生成器 + 热重载 + `校验插件.py` | 7 |
| B6 安装/升级/卸载（原子性、审计、引用检查） | 5 |
| 测试（漂移、签名失败、依赖缺失、7 轴拒绝、卸载残留） | 5 |
| **合计** | **44** |
| （可选）进程隔离后端 + 1 kHz 延迟实测 | +12~20 |

**风险**

1. **"市场"的冷启动**：没有第三方插件时，市场的价值是 0。**建议**：市场机制先服务于**内部**（把现有 6 个算法按新格式打包、走一遍完整生命周期），等真有外部作者再开索引。**不要先建空市场。**
2. **签名密钥的管理**是真实的运维负担（私钥保护、轮换、吊销）。**第一版的诚实降级**：只做"哈希 + 来源 URL 显示"，签名列为 T2 的后续。**但界面上不能宣称"已签名"**。
3. **热重载与仿真状态的交互**：热重载一个正在写 `ctrl` 的插件，会有一步的控制量来自新旧混合。对策：**重载发生在控制周期边界**（现有装配器已有"重新装配整组算法"的边界点），并在界面上提示"重载会重置该插件状态"。
4. **Python 版本与依赖的碎片化**：插件声明 `numpy>=2.0` 但宿主是 numpy 2.2.6——版本冲突无法自动解决。规格要求**明确告知"依赖冲突，无法安装"，并给出宿主版本**，而不是装上再崩。

**风险预算：+6 人日 → 区间 44~50 人日（不含进程隔离）。**

### (e) "假但像样"会是什么样

- ❌ **一个漂亮的插件卡片列表，但"安装"按钮只是把文件拷到目录**：无校验、无版本、无卸载、无审计。识别方法：**装两次同一个插件，看有没有冲突提示**。
- ❌ **声称"沙箱隔离"**。识别方法：**写一个 `import os; os.system('...')` 的插件，看它能不能跑**。
- ❌ **清单与代码不一致也没人管**（清单说支持 6/7 轴，代码硬编码 6）。识别方法：**用 iiwa14 装它**。
- ❌ **索引是手写的 JSON 列表，没有哈希**。识别方法：**改一个下载包的字节，看安装是否报错**。
- ❌ **热重载其实是重启软件**。识别方法：**改一个插件的 KP，看仿真时间是否归零**。
- ❌ **把"危险调用扫描"宣传成安全机制**。识别方法：**读界面文案**——如果写的是"已通过安全扫描"，就是在骗人。

## 9. 状态栏（Status Bar）

### (a) "完整实现"的段落定义

**完整实现 = 一条始终可见、固定高度、不滚动、不弹窗的单行（窄屏可折为两行）状态条；它显示的每个字段都来自唯一的状态源、有明确的取值来源、在"不知道"时显示"未知"而不是 0 或绿灯；刷新率低（不抢带宽）、视觉分级明确（正常/注意/严重三档）、且有一条写下来的"什么不该放进来"的规矩。**

### (b) 功能拆解

**B1 该放什么（十项，按位置从左到右）**

| 位置 | 字段 | 取值来源 | 形态 | 点击行为 |
|---|---|---|---|---|
| 1 | **模型**（显示名 + 自由度） | 资产注册表 + `mjModel.nv` | `UR5e · 6 轴` | 打开资产库 |
| 2 | **项目**（名字 + 未保存标记 `•`） | 项目状态 | `Panda_基础PD •` | 打开项目切换 |
| 3 | **物理状态**（运行 / 冻结 / 暂停 / 故障） | 步进状态机 | 图标 + 文字 | 切换运行/冻结 |
| 4 | **仿真时间** `t = 12.345 s` | 仿真时钟 | 等宽数字 | 重置/归零（需确认） |
| 5 | **实时因子 RTF** `0.99×` | 第 7 项 | 数字 + 三档配色 | 跳到监控页 |
| 6 | **活动算法**（数量 + 生效者） | 装配结果 + `接管控制` 声明 | `算法 3（生效：轨迹跟踪）` | 打开算法面板 |
| 7 | **录制状态**（就绪 / 录制中 `● 00:12` / 回放中） | 录制状态机 | 图标 + 计时 | 停止/打开录制面板 |
| 8 | **未保存更改** | 参数表/项目脏标记 | `未保存` | 跳到需保存的地方（列出） |
| 9 | **连接状态**（仅部署模式显示：`未接入` / `仿真` / `已连接` / `故障`） | 设备状态机 | 图标 + 文字 | 跳到部署页 |
| 10 | **告警计数**（`⚠2  ⛔1`） | 第 7 项告警引擎 | 图标 + 计数 | 打开监控页对应筛选 |

**必须包含"生效算法"这一条的理由**：本项目踩过真实的坑——**多个算法都写 `ctrl[:]`，后装配的整体覆盖前面的，被覆盖的那个界面照样显示"✓ 已加载"，用户完全看不出来**（`软件/插件系统.py` 里 `接管控制` 的注释记录了实测：末端离目标 394.7 mm）。状态栏是**唯一常驻可见**的位置，把"当前谁在真正控制"常驻显示出来，这个坑就不可能再被静默掩盖。**这是状态栏对这个项目最有价值的一项信息。**

**B2 什么不该放进状态栏（这就是"规矩"）**

| 不放 | 理由 | 应该在哪 |
|---|---|---|
| 错误堆栈 / 日志流 | 状态栏不是日志 | 日志面板 / 终端 |
| 可编辑控件（输入框、滑杆、下拉） | 状态栏是"显示"，编辑会带来焦点与误操作 | 对应面板 |
| 滚动内容、跑马灯 | 更新率无上限，抢注意力 | 通知中心 |
| 详细数值表（每关节误差、每通道队列） | 一行放不下，且变化太快会闪 | 监控/诊断页 |
| 全局搜索框 | 它是工具不是状态 | 顶栏 |
| 峰值/历史统计 | 需要上下文 | 曲线面板 |
| 各类"一键"按钮（保存/导出/清空） | 误触代价高 | 菜单/面板 |
| 未实现功能的灰色按钮 | 假可用性 | 不要出现 |
| 单次操作的 Toast 常驻 | Toast 归 Toast | 通知 |

**核心规矩一句话**：**状态栏只回答"现在是什么状态"，不提供操作、不显示历史、不承载长文本。**（可点击跳转不算"操作"——它只导航。）

**B3 显示纪律**

- **固定高度**，不因内容变化而改变布局（否则整个界面会跳）
- **数值等宽字体**（仿真时间、RTF 跳动时不能左右晃）
- **刷新率受控**：RTF/仿真时间 ~5 Hz（人眼够，且不抢带宽）；状态类字段**变化时才发**（沿用现有 `项目状态发布器` 的"指纹比对、变了才发"思路——这个模式已经在项目里跑了，直接复用）
- **三档视觉**：正常（中性）/ 注意（黄）/ 严重（红）。**只用颜色不够**（色盲），必须配图标或文字
- **"未知"是合法值**：模型还没加载时显示 `—`，不是 `0 轴`；未接入硬件时显示 `未接入`，不是 `已连接`
- 窄窗口（< 900 px）折两行，**优先保留 1/3/5/6/7**（模型、物理、RTF、算法、录制）

**B4 与桌面壳的关系**

Web 版本里，状态栏是应用窗口的最底部固定条（不是浏览器状态栏）。如果将来做远程访问，状态栏反映的是**服务端**的状态，并且必须标明"远程 · 延迟 8 ms"（避免把远程延迟误当成仿真变慢）。

### (c) 数据/状态模型

```
状态栏快照 StatusBarState（一次推送的完整状态，不推送增量）
  ├ 模型: {id, 显示名, 自由度, 状态(加载中|就绪|错误)}
  ├ 项目: {名, 脏标记}
  ├ 物理: {状态(运行|冻结|暂停|故障), 上次故障原因?}
  ├ 时间: {仿真时间, 墙钟时间}
  ├ 实时: {rtf, 采样窗口秒数}          ← 必须带窗口，否则单点 RTF 会跳
  ├ 算法: {总数, 生效者名单[], 冲突警告?}
  ├ 录制: {状态, 已录时长, 文件?}
  ├ 连接: {模式(仿真|真机|未接入), 名称?, 往返延迟?}
  └ 告警: {注意数, 严重数, 最近告警id?}

推送策略: 变化驱动（指纹比对）+ 5 Hz 心跳兜底
```

### (d) 工作量与风险

| 工作包 | 人日 |
|---|---|
| 状态源整合（把 5 个模块的状态聚合成一个 `StatusBarState`，含"未知"语义） | 5 |
| 状态栏组件（三项响应式、等宽数字、三档视觉、点击跳转） | 4 |
| 刷新策略（指纹比对 + 变化驱动 + 心跳兜底 + 5 Hz 限流） | 2 |
| 与告警引擎、录制状态机、设备状态机的接线 | 3 |
| 测试（未知值、窄屏折行、告警去抖联动、状态栏不变形） | 2 |
| **合计** | **16** |

**风险**

1. **状态源分散**：这 10 个字段来自 5 个不同模块，每个都可能"还没初始化"。若不做统一的"未知"语义，状态栏会成为"启动时显示一堆 0"的重灾区。**对策：先定 `StatusBarState` 与"未知"的表示，再接数据。**
2. **性能上的假问题**：状态栏本身几乎无开销；风险在于**为了它而提高其他模块的推送频率**（例如为了显示 RTF 把指标桥提到 30 Hz）。**规定：状态栏只消费已有推送，不新增数据源。**

**风险预算：+2 人日 → 区间 16~18 人日。**

### (e) "假但像样"会是什么样

- ❌ **硬编码的"已连接"绿灯**（参考实现的健康检查 `ok` 硬编码为真，就是这个）。识别方法：**拔掉硬件/断掉后端，看它是否变红**。
- ❌ **RTF 显示 1.00× 但仿真明显在慢慢爬**。识别方法：**同时看仿真时间与墙钟时间**。
- ❌ **"算法 3 已加载"但不说是谁在生效**：正是这个项目已经踩过的坑。识别方法：**同时挂两个写 `ctrl` 的算法，看状态栏是否警告**。
- ❌ **未保存标记永远不亮**（脏标记没接）。识别方法：**改一个参数不保存，看是否出现 `•`**。
- ❌ **状态栏随内容抖动**（字数变化导致布局跳动）。识别方法：**让仿真时间从 9.9 s 走到 10.0 s**。

### 10.2 承重项：哪 2~3 项撑起其余

**判断标准**：拿掉它，其他项是否要重做（而不是"少一个功能"）。

#### 承重项 ①：**L0 状态与传输契约 + 观测核心**（跨越第 5、7、9 项的公共内核）

**理由（最强的三条）**：

1. **第 5、7、9 项是同一份采集的三个视图。** 诊断要的通道、监控要的计数器、状态栏要的状态，**来源完全重合**（`mjData`、计时器、队列计数、插件错误计数）。分开做 = 写三遍采集 = 三处数据对不上，而且**开销叠加三倍**（这对一个"物理步只需 3.39 µs"的系统是致命的）。
2. **它是第 1 项质量的前提。** 轨迹规划的价值一半在"结果可信"——**贴合报告、约束回代校验、跟踪误差**全部是采集层的数据。没有观测核心，"时间最优"就只是一条好看的曲线（这正是 (e) 里第一个假实现）。
3. **它决定 Web 界面的成败。** 现有 5 个桥的语义（Snapshot 最新覆盖、按频率分通道、指纹比对去重）是**踩坑换来的**（用错消息类是"按 Start 完全没反应且不报错"的真实事故）。新界面如果重造一套推送，这些坑要重踩一遍。

**证据**：本项目的整个"界面↔仿真"通信史，就是一部"通道设计错→静默失效"的历史（`录制桥.py` 文件头记录了两起同源事故）。

#### 承重项 ②：**L1 无头仿真服务**

**理由**：

1. **它是"换了技术栈还能不能干活"的唯一验证点。** 现在所有仿真都跑在 `mujoco.experimental.studio` 的 `launch_thread` + `StepControl` 里（官方标注 experimental，11 周改过 4 次）。**这个依赖不解除，Web 界面就是盖在流沙上**：官方一变，物理线程和界面一起完蛋。
2. **它决定"实时因子"这个产品级指标能不能被控制。** 现状 0.86×，其中一部分是官方节拍器的钳制（LE 报告 §6.2）。脱离它，RTF 才从"偶然结果"变成"我们的指标"（第 7 项的核心展示对象）。
3. **所有九项都在它上面跑**：没有它，参数表改不了模型、轨迹没法执行、诊断没有采集点、部署没有仿真后端。

#### 承重项 ③：**L2 资产注册表 + 场景图导出**

**理由**：

1. **它是唯一"没有替代路径"的项。** 其他项都有降级方案（没有诊断可以看曲线，没有市场可以手动拷文件），但**没有场景图就没有 3D 视口**——而这是软件的主界面。参考实现把 378 MB 资产无治理地塞进构建产物（`dist/` 424 MB），反面教训明确了：资产管线不是"以后再说"的事，**它是第一个必须做对的 IO 边界**。
2. **它是"多机器人"这个项目核心主张（2/6/7 轴、5 台内置 + 24 台可导入）的物理载体。** 资产注册表同时是参数表（限位/质量从哪来）、轨迹规划（约束从哪来）、诊断（饱和阈值从哪来）的**共同输入**。这个"元数据单一事实来源"如果晚做，后面每一项都会各自手敲一份限位表——参考实现正是这么干的，而且**限位表被复制了 3 份并发生漂移**。

**为什么不选第 1 项（轨迹规划）作为承重项**：它是**功能价值最高**的一项（现有能力缺口最大），但它**依赖 L0/L1/L2/L5**，且它的产出（轨迹）不是其他项的输入。它是"上层建筑"，不是"承重墙"。同理，部署虽然风险最高，但它的大半（安全层、抽象层）**可以独立并行**，不阻塞别人。

- **M3 之后**：如果 6 个人月只换来"和原来一样的 8 个面板"，那么第 1、3、5、6 项（真正的新功能）才是这个项目的价值所在，**资源应立刻全部转向它们**，界面美化降级。

> **读法（四条，缺一条就会算错）**：
> 1. **"含风险预算"列是上限口径，"估算"列是工作量口径**，两列**不要相加**，也不要把两列的合计混着引用。
> 2. **第 0 行（观测核心）单独列出，是因为它被第 5、7、9 项共同使用**——第 1~9 项的表内合计（380）里**不含**它，所以 **394 = 380 + 14** 才是九项的真实预算，也才能与 §1~§9 各表 (d) 里写的合计对上。

> **不要做的两件事**：① 不要把"换壳 137"加上"九项 394"（重复计了 L0~L5）；② 不要把九项明细直接相加当总数（漏了外壳与地基 58 人日）。

**必须一起读的四条诚实边界**：

1. **452 人日 ≈ 21 人月 ≈ 单人全职 21 个月**（不是"几周"）。任何"一个月做完九项"的说法都必然包含大量 (e) 类假实现。
2. **第 6 项的真机部分不在这 452 人日里**：EtherCAT 一条就是 **+3~6 个月**，且很可能需要换到 Linux（见第 6 项 (d) 风险 2）。
3. **多人协作不是简单的除法**：L0 契约必须先冻结，前端与后端才能真正并行；集成与回归测试天然串行。两人协作的现实系数是 **1.6~1.9**，不是 2.0——**这也是为什么 L0 是第一个承重项**。
4. **本估算不含**：产品设计讨论、美术/视觉设计、跨平台打包（Windows/Linux）、真机安全评审与认证、文档与用户手册。

## 〇、这份方案要解决什么

自检报告的结论是一句话：**"LE 有壳没核，驭臂有核没壳；最优解是把驭臂的核装进 LE 那样的壳里。"**

本方案加上四条硬约束（用户 2026-10-16 补充）：

| # | 约束 | 对方案的影响 |
|---|---|---|
| 1 | 以自检报告为基础，充分学习 LE：产品叙事 / 界面 / 架构 / 轨迹规划 | 四样都要，但**假数据一律不抄**（自检报告 §3.3 已列清单） |
| 2 | **仍旧是桌面软件**（双击打开的那种） | 不做"浏览器里开个 localhost 服务"的形态；必须是 `.app`/`.exe` |
| 3 | 大不了完全绕过官方 ImGui 绘制层，界面自己写；**原有功能与优点一样不能少** | 界面层重写，但 10 个面板、5 套风格、中英双语…全部要有对应物 |
| 4 | 九项功能（轨迹规划 / 3D / 参数表 / 资产库 / 诊断 / 部署 / 监控 / 插件市场 / 状态栏）**彻底完成**，不做一半 | 目标从"换个壳"升级为"重做一个完整工具"——工程量口径必须重算 |

**⚠️ 口径先说清**（这是本方案最重要的一句话）：

> 自检报告里"换外壳 0.57~0.90 万行、2~4.5 人月"这笔账，**只覆盖约束 3**（把现有能力搬过去）。
> 约束 4 的九项新功能**另算**，实测口径 **442 人日 ≈ 20 人月**（单人 20~21 个月，两人 11~13 个月）。
> 也就是说：**137 人日是"换壳"，305 人日是"新功能"**。任何把两者混在一起的估算都会误导排期。

## 一、技术事实（本次实测，决定了架构能怎么选）

这一节只写**已经跑出来的事实**，不写推测。

### 1.1 自检报告里那条"Filament 不能被外部创建"的结论，只对了一半

| 事实 | 证据 |
|---|---|
| `mujoco.experimental.studio.renderer` 是个**坏的**扩展模块，任何 gfx 模式都崩在 `pbr.filamat` | `strings` 对比：`renderer*.so` 有 25 处 `.filamat` 但 **0 处 `assets`**；`native_viewer_cc*.so` 有 `assets` |
| `native_viewer_cc.Viewer` **是好的**，`InitRenderer` 成功、`RenderToTexture` 可出图 | 隔离子进程实测：exit 0，无 `MUJOCO_LOG.TXT` 追加 |
| `classic` 这个 gfx 模式 = **经典 OpenGL 渲染器，根本不需要 Filament** | `include/mujoco/experimental/studio/hal/graphics_mode.h:23-47` |
| **我们自己起窗口 + 自己建 GL 上下文 + `mjr_render` 直接画**，这条路走通了 | 参考实现已产出（自研窗口 2560×1440 截图，exit 0） |

**性能实测**（自研窗口 + `mjr_render`）：

| 帧缓冲 | 阴影 + 平面反射 | 都关 |
|---|---|---|
| 2560×1440 | 11.4 ms/帧（88 fps） | 1.4 ms（736 fps） |
| 3840×2160 | 13.8 ms/帧（72 fps） | 1.5 ms（665 fps） |

**离屏渲染备份路径**：`mujoco.Renderer` 720p = 7.9~16.4 ms/帧（61~126 fps）。

### 1.2 一个必须尊重的硬约束：兼容 profile vs 核心 profile

官方文档：MuJoCo 用 **OpenGL 1.5 兼容 profile + `ARB_framebuffer_object`**。实测：

```
core 4.1 上下文   → moderngl ✓ 着色器 ✓，但 MjrContext ✗ FatalError: ARB_framebuffer_object required
legacy 2.1 上下文 → MjrContext ✓ mjr_render ✓，但 moderngl ✗ Requested OpenGL version 330, got version 0
```

**含义**：在 macOS 上 **moderngl / pyglet 2.x 无法与 `mjr_render` 共用同一个上下文**。
唯一验证过的主机组合是 **`glfw`（MIT）+ `PyOpenGL`（BSD）** —— 两个都已在 `.venv` 里。

### 1.3 WebView 外壳：三条路线，全部收敛到同一个必须先做的验证

| 路线 | 原生 3D 放进同窗口 | 新语言 | 结论 |
|---|---|---|---|
| **Tauri v2**（Rust） | ✅ `Window::add_child` + `Webview::with_webview` —— **唯一两半都有官方文档的** | Rust + C++ + Python | 最稳，但语言最多 |
| **pywebview**（Python） | ✅ `window.native` 就是真的 `NSWindow`（源码 `cocoa.py:595`） | **零**（纯 Python） | 最快、语言最少 |
| **`webview/webview`**（C++） | ✅ 窗口是自己建的，同级视图是天经地义 | **零**（已是 C++） | 架构最贴，但要自己管安装包/更新 |

**两个关键发现**：

1. **同级视图布局不需要"透明"**（只要能把 webview 摆到 3D 以外的矩形）。这一点极其重要：
   macOS 上"透明 webview"靠的是**私有 API**（KVC `drawsBackground`），Tauri/Wails 都把它藏在
   构建开关后面。**避开透明 = 避开私有 API = 不堵死 Mac App Store 与未来 macOS 升级。**
2. **Wails 出局**：v2/v3 都没有公开的原生窗口句柄 API，想把原生 3D 放进去必须 fork 它。

**所有路线共同的、必须先验证的未知**：

> 一个 Metal/Filament（或 GL）原生视图，能不能作为 **WKWebView 的同级视图**放进同一个
> `NSWindow` 而不出现合成瑕疵？（Windows 上同理：子 HWND 并列）

**这个验证必须最先做**——它决定后续架构，不是框架问题。约 200 行 Cocoa 原型即可定论。

### 1.4 官方 Studio 层在 Windows 上能不能用：**仍然未确认**

自检报告 §E.5 把这个列为"跨平台工作的第一个调查项"，本次**没有解决**（无 Windows 机器）。
它决定跨平台是"补一层"还是"换底座"。**因此本方案不把跨平台押在 Studio 层上**（见 §3 的分层）。

### 2.0 为什么不要 Node 边车（本次取证）

LE 的真实架构是 **Vite:3000 / Express:3001 / 每请求 spawn 一个 Python**，只有 **2 条路由**
（`GET …/health`、`POST …/run`）。那个 `api.mjs` 的 151 行**零业务逻辑**——只有进程与 JSON 管道，
唯一有含量的是"Python 错误写 stdout 且 exit 1，Node 用 `if (parsed) resolve` 保留它"。

**结论**：它存在的唯一理由是"浏览器不能 spawn 进程"。我们的 Python 侧本来就在跑，
**直接由 Python 起本地服务即可**（P0 已经这么做了），省掉一个进程、一次序列化、一次冷启动。

**另外两条要避的**：
- **每请求 spawn 一个 Python**（无池化、无队列）——冷启动 + 重复 import numpy 的开销每请求付一次。
  我们用**常驻进程 + 消息通道**，这个问题根本不存在。
- `docs/ALGORITHM.md` 描述的 `strategyId / stageConfig / algorithmMeta / stageMetrics / debugLogs`
  等标识符在代码里**命中 0 次**——**文档描述了一套不存在的架构**。我们文档必须与代码同步验收。

### 2.1 移植 LE 规划算法时必须纠正的三处缺陷

> 依据：`报告/03_对标与调研/LoongEnv-SHIZE源码学习笔记.md`（1758 行，38 个源文件经 git blob SHA-1 逐字节校验）。
> 该笔记不满足于读代码——它**用仓库自带的真实运行产物 `docs/planning_demo_summary.json` 反向验算**，
> 9 段里 8 段逐位复现。以下结论是**算出来的，不是猜的**。

1. **`v_max/a_max/j_max` 是路径参数空间（`s∈[0,1]`，单位 1/s、1/s²、1/s³）的量，不是关节量**，
   却被界面标成"关节速度约束" —— 照抄会误导用户。
   正确做法：**界面上分别暴露 s 空间与关节空间两组约束**，并明确标注各自作用域。
2. **`qd/qdd` 用 `np.gradient` 数值微分算，不保证满足约束** —— 而算法内部其实**已经有**
   `sd_path/sdd_path` 和样条导数可用，属于"放着现成解析量不用"。
   必须改为链式法则解析求导 + 逐点回代校验，把"**约束满足率**"作为规划结果的验收项。
3. **硬编码 6 轴**（CSV 强制 `J1..J6`、限位强制 6 值，贯穿三层）—— 我们库里有 **7 轴的 iiwa14**
   和 **2 轴的夹爪模型**。规格要求：**任何地方出现字面量 6 都算缺陷**，必须有 2/6/7 轴回归用例。

### 2.1.1 ⚠️ 反向验算新发现：参考实现的规划器**不能直接照搬**

这四条是本次新增的、比上面三条更严重的发现（同样来自对真实产物的反向验算）：

| # | 发现 | 后果 |
|---|---|---|
| 1 | 时长 14.350 s ≈ 加速度受限下界 `2√(1/a_max) = 14.142 s` ⇒ **`v_max` 与 MVC 衔接速度从未生效**，全靠 s 空间 `a_max` 支配（而且 `pipeline.py:602` 把 `v_max` 用 `max()` 当**下限**用了） | "速度约束"这个滑杆在当前默认参数下**是装饰** |
| 2 | 后 6 段的 Ruckig 回退阶梯**全部掉到第③档"保持原速"**，5 个 MVC 极小点（s≈0.75→0.97）**一个减速都没产生** | **分段机制在默认参数下形同虚设**——这恰恰是它自称最讲究的部分 |
| 3 | 末段终止速度实测 `0.1018 ≠ 0`（物理上需要 0.259 长度、只有 0.034），**靠 `pipeline.py:720-722`+`:680-681` 事后强行置零掩盖** | **终端速度不连续 → 真机不可执行**。这是"看起来能跑"的典型 |
| 4 | 平滑做了 60 遍却**没有偏差校验**（`warnings` 数组全程恒空） | 平滑可能已经改变了轨迹而没人知道 |

> 📌 **结论修正**：LE 的规划器**不是成品级**，而是"**用对了 TOPPRA 官方 API 的原型**"
> （已考证：`build_toppra_instance` + `compute_mvc_profiles` 是 TOPPRA 官方
> `plot_robust_kinematics.py` 的逐行移植，连 argparse 默认值都一样——用对 API 是好信号，
> 但**没有工程化**）。所以我们的做法是 **重实现 + 带校验**，不是移植。

### 2.1.2 移植时先做的最小四步（成本极低、立刻暴露问题）

| 序 | 做什么 | 收益 |
|---|---|---|
| 1 | **先加校验**：`max|q̇|≤vlim`、`max|q̈|≤alim`、`s_dot[-1]==0`、平滑偏差 ≤ tol | 立即可见上面四个缺陷，也就立刻知道"哪里不能抄" |
| 2 | `q̇/q̈` 改**链式法则**解析求导（别用 `np.gradient`） | 约束才真的成立 |
| 3 | `v_max/a_max/j_max` 换成**关节/笛卡尔量**，并按路径长度自动换算 | 治本：界面语义与实际作用域一致 |
| 4 | 机器人模型**参数化**（轴数、限位、FK 全从 `mjModel` 取） | 2/6/7 轴都能跑 |

**UI 必须回显**：每次规划后显示"**实际最大关节速度/加速度/加加速度 vs 各自限制**"。
这一条同时是"假实现识别法"——真规划器答得出这个问题，假的原型答不出。

### 2.2 许可证（动手前必须定）

| 组件 | 许可证 | 处置 |
|---|---|---|
| `toppra` / `ruckig` | MIT | ✅ 可用 |
| `ecos`（TOPPRA 默认求解器） | **GPLv3** | ❌ 与本项目 MIT 发布冲突 |
| **`cvxpy` + Clarabel** | Apache-2.0 | ✅ **已实测数值完全等价**（时长差 0.0000s、关节角差 0.000000 rad），代价是**慢约 32 倍**（5s → 165s） |

**结论**：默认走 `cvxpy + Clarabel`，把"慢"设计进体验（离线规划 = 点一次、等 1~3 分钟出轨迹）。
**不得**把 ecos 打进分发物。

## 三、架构：三层切开，只在中间留一条窄缝

这是本方案的核心决定，也是约束 3 的落地方式。

```
┌──────────────────────────────────────────────────────────────┐
│ ③ 界面层（Web：React + Tailwind）                             │
│    任务流导航、参数表、图表、诊断、监控、资产库、插件市场…    │
│    ★ 天然跨平台：三家系统上是同一份代码                        │
├──────────────────────────────────────────────────────────────┤
│ ② 契约层（消息 schema + 命令 API）  ← 唯一允许的通信方式      │
│    现在：WebSocket + JSON（**P0 已通，实测 434 帧 0 丢弃**）  │
│    将来：同一份 schema，换传输不影响两侧                       │
├──────────────────────────────────────────────────────────────┤
│ ① 仿真与算法层（纯 Python + MuJoCo，**无界面耦合**）           │
│    物理步进 / 控制算法 / 参数辨识 / 数据录制 / 7 个桥接层       │
│    ★ 自检报告 §A.2 已取证：这一层**天然就是无界面耦合的**      │
├──────────────────────────────────────────────────────────────┤
│ ①b 窗口与 3D 层（可替换，接口固定）                            │
│    选项 A：官方 Studio 窗口（classic 渲染器）—— 便宜、质量现成 │
│    选项 B：自研窗口 + glfw + mjr_render —— 完全自主、跨平台    │
│    ★ 两者对 ① 的接口相同 → **可以先用 A 再用 B，不是二选一**   │
└──────────────────────────────────────────────────────────────┘
```

### 3.1 为什么这样切

- **①天然可复用**：自检报告 §A.2 逐条取证过——7 个桥接层 `grep imgui` 全为 0、
  官方消息是纯 Python dataclass、算法层不依赖任何界面模块。**所以重构不必重写逻辑层**。
- **②是唯一的耦合点**：界面只通过消息说话，绝不直接 import 界面/平台 API。
  这条纪律同时买到跨平台（界面层不碰系统 API）与可测试性（可以拿假数据喂界面）。
- **①b 可换**：把窗口层做成"可替换实现"，就不必现在就赌 Filament 能不能搬。
  **先用便宜的（A）把界面跑起来，等 spike 有结论再决定要不要 B。**

### 3.2 对官方 Studio 层的最终态度

**分阶段脱钩，不是一刀切**：

| 阶段 | 依赖 Studio 的部分 | 目的 |
|---|---|---|
| **现在 → M2** | 窗口 + 3D + 渲染（仅此两样） | 界面改造期间保持软件可用、能对照验收 |
| **M3 起** | 无（窗口层换成自研，`插件系统.py` 那 14 处 Studio 引用改指向我们自己的消息定义） | 跨平台成为"加一个实现"而不是"重构" |

`插件系统.py` 是全项目**唯一**直接 import 官方实验 API 的文件（自检报告 §1.1），
所以这次脱钩的爆炸半径是**一个文件**——这是当初收敛依赖边界的回报。

### 5.1 最重要的一条判断：九项不是九个模块

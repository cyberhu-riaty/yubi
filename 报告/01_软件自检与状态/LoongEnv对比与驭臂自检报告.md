## 〇、结论摘要

**你的观察是对的，但要分清"哪一层"更好。**

LE 的界面确实明显更好——因为它用的是 **2026 年主流 Web 技术栈**（React 19 + Tailwind 4 + Motion + three.js），而驭臂用的是 **MuJoCo 官方 ImGui 工作台**（C++ 编译进去的，字形/焦点/布局都改不动）。这是**载体差异，不是设计水平差异**。

但把两边代码摊开看，结论会反转一部分：

| | 驭臂 | LE |
|---|---|---|
| **本质** | 真在跑物理引擎的**工具** | **原型展示**（自述 "原型展示"，`metadata.json:3`；包名还叫 `react-example`） |
| **界面观感** | 受宿主框架限制，中规中矩 | **明显更好** |
| **真能干的活** | 离线仿真 + 自写控制算法 + 参数辨识 + 数据录制 | 轨迹规划（TOPPRA+MVC+Ruckig）**一项是真的**，而且做得不错 |
| **界面里有多少是假的** | **无假数据** | **大量 mock**：Deploy 整模块、SystemMonitor、Diagnose 的力矩公式、状态栏 |
| **最严重的缺陷** | 界面受制于宿主框架 | **换机器人只换 3D 壳，规划恒算 ER15**；健康检查 `ok` 硬编码为真 |
| **工程纪律** | 强（出错隔离 / **24 项**接口合同 / 哈希自检 / 514 项断言） | 弱（**无测试、无 CI（且被主动删除）、无 LICENSE、无 i18n**） |
| **架构自由度** | 被宿主框架绑死（macOS + Python + ImGui） | 自由（Web 栈，天然跨平台） |
| **依赖健康** | 版本锁 + 离线依赖，无废弃依赖 | `mujoco-js@0.0.7` **已被 npm 弃用**却是唯一 3D 加载器；5 个死依赖 |

**一句话**：LE 是**"界面原型 + 一个真算法"**；驭臂是**"真工具 + 一个憋屈的界面"**。你看中 LE 的界面，看的其实是**你已经算过账、但没下决心做的那件事**——换外壳。

**最关键的一条**：驭臂自己的报告里已经算过这笔账——换外壳 **0.57~0.90 万行、2~4.5 人月**（`优化…/报告/README.md` 索引行）；LE 用 3850 行 TypeScript 做到了（`src/` 实测 3850 行）。**LE 不是新答案，是那个已知答案的一份廉价样机。**

## 一、两个软件到底是什么（定性）

### 1.1 驭臂：站在官方肩膀上做的真工具

- **定位**：桌面端机器人仿真软件，双击即用，控制算法可自写自换（`文档/驭臂_完整工作报告.md:60`）
- **解决的核心问题**：原来"改个控制参数要开文件改数字重跑、看不到曲线"，变成"拖滑杆即时生效 + 实时曲线 + 录制 + 辨识"（同上:65-68）
- **技术底座**：**MuJoCo Studio**，分三层——我们写的 Python 外壳 / 官方 Python 层（实验性）/ 官方 C++ 层（16 个 `.so`，改不动也拷不走）（同上:70-85）
- **规模**：`软件/` **9778 行 Python**，35 个文件；算法库 6 个插件共 1309 行
- **路线选择**：明确否掉了"直接用官方"（要改 C++ 才能加算法）和"fork 官方"（上游 30 天一个版本，合并冲突噩梦），选**方案 C：用自己的外壳包住官方底座**（同上:276-296）
- **依赖边界是显式合同**：全项目**唯一**一个直接 import 官方实验 API 的文件是 `软件/插件系统.py`（`:2, 30-60`），其余代码一律通过它间接使用官方能力；`软件/骨架/官方接口清单.py:33-48` 列出全部允许使用的 **13 个官方模块**

**启动到机械臂动起来的真实调用链**（可逐行核对）：

```
主程序.py:193  main
  → :262      版本自检
  → :270-277  24 项官方接口自检
  → :135-136  项目装配（读 项目/*.json 决定挂哪些算法）
  → :340-341  安全注册表 + ViewerConfig
  → :371      启动.启动外壳
       启动.py:84   make_thread_endpoints
         :95,598    起后台仿真线程（macOS 要求窗口必须在主线程，故线程对调）
         :120-125   加载 model/data
         :363-365   注册内置重力应用器 + 冻结判据
         :536       每圈派发 StepEvent
              ↓ 官方 StepControl 插件执行 mj_step（★ 真正推进物理的是它，不是 sync）
              ↓ 用户算法写 event.data.ctrl[:]
         :569-573   回发 StateSnapshot
         :576       sleep(0.0002)
         :652       主线程 run_native_viewer
```

> 📌 上面这条链路里藏着驭臂踩过的一个大坑，它自己写进了 `软件/插件系统.py:281`：**"真正把物理往前推的是官方 StepControl 插件，不是 ViewerHandle.sync"**——`sync` 只负责派发事件。若没把 `StepControl` 一起注册，控制律会被调用 25 万次而仿真时间停在 0，机械臂纹丝不动。这种知识只有真做过才知道。

### 1.2 LE：一个界面原型，带一个真算法

- **自我定位**：`metadata.json:3` 写着 **"LoongEnv 4D+Core 工业机器人AI开发平台原型展示"**；npm 包名 **`react-example`**（`package.json:2`）
- **README 原话**："First version uses local one-shot planning requests (no queue/streaming)"（`README.md:61`）
- **真实现状**：四个模块里只有轨迹规划是完整实现，Deploy/Monitor 是静态展示
- **规模**：`src/` 3850 行 TS/TSX（13 文件）+ `server/` 189 行 + Python 算法 1167 行

> 📌 **定性差别**：驭臂是"我造了个工具在用"；LE 是"我做了个样板给人看"。这决定了后面所有对比的解读方式——**LE 的很多"优点"是原型才享有的特权**（不用管错误处理、不用管持久化、不用管真实硬件）。

## 二、架构差别（五个维度）

| 维度 | 驭臂 | LE |
|---|---|---|
| **渲染 / 3D** | 官方 **Filament PBR**（C++，金属反光质感） | **three.js + @react-three/fiber**（WebGL，浏览器内） |
| **物理** | **真跑 MuJoCo 物理**（`StepControl` 推进 `mj_step`） | **只算正向运动学**（`mj_forward`），无动力学（`SimulationView.tsx:961`） |
| **界面框架** | ImGui（C++ 编译进 `.so`）+ Python 自研面板 | React 19 + TailwindCSS 4 + Motion |
| **进程模型** | 单进程 Python，窗口在另一线程 | 三进程：Vite(3000) + Node 边车(3001) + Python 子进程 |
| **跨平台** | ❌ **仅 macOS**（字体补丁依赖 STHeiti，glfw 需特修） | ✅ 理论全平台（Web 栈） |

### 2.1 最本质的差别：物理 vs 运动学

这是**唯一一条无法用工程量弥补的差别**。

- 驭臂：`安全注册表` 里明确写道"真正把物理往前推的是官方的 StepControl 插件"（`软件/插件系统.py:281`），并为此搞了"世界冻结闸门"来控制物理启停。**它是在跑真的动力学**。
- LE：`SimulationView.tsx:961` 只调 `mj_forward`（正运动学），播放靠 `requestAnimationFrame` 把规划好的关节角插值后 `setJointValue()` 喂给模型（`:882`、`:988`）。**它是在播一段预先算好的动画**。

**含义**：LE 能演示"机械臂按规划轨迹动起来"，但**不能回答"这个控制器在这个模型上稳不稳"**——因为它压根没有控制器，也没有动力学。而驭臂的主战场恰恰是后者。

### 2.2 扩展机制：驭臂有真契约，LE 没有

**驭臂的控制算法契约**（`软件/插件系统.py:111-140`）：类属性 `名称/版本/说明/作者` + `接管控制`；**必须**有 `@每步` 且参数类型标注为 `messages.StepEvent` 的方法（不写标注官方直接报错）；另有 7 个可选钩子（`插件状态`/`可调参数`/`设置参数`/`收到模型`/`模型兼容性`/`绑定模型路径`/`模型已切换`）。最小骨架见 `算法库/通用/我的控制律_模板.py:47-90`，**90 行内含注释**。

发现机制也比想象中讲究：扫描只读文件不 import（`软件/项目.py:378-407`）；按文件路径生成唯一模块名并**先清 `sys.modules`**，解决同名文件互相覆盖（`软件/装配器.py:49-76`）；找类用四级规则（继承 `控制插件` 优先，鸭子类型兜底，`:157-196`）；**重名直接拒绝**（`:294-297`）；不兼容的插件预检后不启用（`:210-238`）。

**LE 的"Plugin"不是插件机制**：四个 `*Plugin.tsx` 是**硬编码 import 的模块**（`App.tsx:51-54`），契约只是一个 `metadata` 对象（`DefinePlugin.tsx:65-67`）。没有发现机制、没有生命周期、没有第三方挂载点。加一个模块必须改 `App.tsx`。

> 📌 **反差**：驭臂在这一层是**真插件机制**，LE 只是命名像插件。
>
> ⚠️ **一处需要更新的旧结论**：驭臂自己的 `文档/架构对比_模块算法封装_对照Ultralytics.md:55` 批评"激活机制是硬编码列表，加算法要改 `主程序.py`"。**这条已经过时**——`软件/项目.py:6-11` 明确把那段记为"在这之前"的旧状态，现已改为：
> ```
> 算法（写一次）──► 项目文件（一份 JSON）──► 外壳按它 new 出插件实例
> ```
> 即 `项目/*.json` 是"哪个模型用哪些算法"的**唯一数据源**，加算法确实不用改外壳代码。本次实测也印证：`--自检` 输出【已加载 0 个算法（项目：iiwa14_基础PD）】，因为该项目**有意**不声明算法；而 `项目/Panda_基础PD.json` 等 5 个项目各自绑了算法集。
> **结论：驭臂"算法激活"这一缺口已闭环，旧报告该条应作废。**

### 2.4 数据类型与复杂度

- **驭臂**：6 自由度以上通用，模型库 5 台 + 24 台可导入（`工具/模型清单.json`），项目机制把"模型+算法+参数"绑成声明文件
- **LE**：**硬编码 6 轴、硬编码 ER15**。规划桥 `build_er15_robot_model()` 写死 DH 参数（`scripts/planning_bridge.py:53-72`），限位校验强制 6 值（`:96-97`）——而它的资产库里有**2 轴的 MP600**（`robotCatalog.ts:107`），根本走不通

### 2.4.1 LE 的算法是真的：TOPPRA + MVC + Ruckig 分工（值得学习的一点）

LE 唯一扎实的部分就在这儿，而且它的建模选择相当讲究：

| 环节 | 实现 | 作用 |
|---|---|---|
| 路径准备 | `prepare_path`（`pipeline.py:213`） | `ssMode='arc'` 走**末端弧长**参数化（用 FK 算，`:240`）；`'time'` 走等距（`:237`） |
| TOPPRA | `build_toppra_instance`（`:281`） | 时间最优参数化：关节速度约束（`:291`）+ 关节加速度约束（`:292-295`），外面再包一层 `RobustLinearConstraint`（`:296-300`），solver = `ecos`（`:305`） |
| **MVC** | `compute_mvc_profiles`（`:309`） | **MVC = `X[:,1]` 这条速度上包络**（`:315`）。它既当曲线展示，又当**分段依据**——其局部极小值成为段交界速度 |
| Ruckig | `plan_segmented_ruckig_from_mvc`（`:566`） | 对**路径参数 s 做 1-DoF jerk 受限整形**（`:478-541`），带 4 级回退速度阶梯（`:615-646`） |
| 映射回关节 | `map_path_to_joint_trajectory`（`:671`） | `qs = path(ss)`，`qds/qdds = np.gradient(...)`（`:677-678`） |

> ⚠️ **最关键的建模事实，也最容易误读**：`v_max / a_max / j_max`（`pipeline.py:39-42`）是**路径参数 s 空间**的量，**不是关节空间的量**。关节约束只通过 TOPPRA 那条路间接进入。所以界面上标着"关节速度约束"的滑杆，实际作用域和用户的直觉不一致。
>
> 📌 这是 LE 真正值得学的地方：**它的规划算法是成品级的**，MVC 同时用于可视化和分段决策这个思路很干净。驭臂的 6 个算法都是关节空间 PID/轨迹级，**没有这一层时间最优参数化**。

### 2.4.2 LE 的算法层封装问题

可替换性**名不副实**。唯一较干净的缝是 `run_mvc_ruckig_pipeline`（`pipeline.py:696`）→ `PipelineResult`（`:63-83`），但**没有策略接口、没有注册表**——文档里承诺的 `algorithm.strategyId`（`docs/ALGORITHM.md:53`）在代码中**不存在**。换算法要动 **5 处**：`pipeline.py` → `planning_bridge.py:237-267, 270-324`（逐字段读取内部结构，强耦合）→ `__init__.py:1-36` → `types.ts:138-147` → `DesignPlugin.tsx:174-187`。

另有 **3 个近乎重复的入口**：`core.run_core_pipeline`（`core.py:61`）、`cli.py:109`、web 路径，三者 web 都不用；同一套参数默认值被抄了 **4 遍**（`core.py:20-33`、`planning_bridge.py:141-155`、`cli.py:66-100`、`DesignPlugin.tsx:32-45`）。

### 2.5 资产与依赖治理

- **驭臂**：`模型/` 108MB 入库（自带各上游 LICENSE），`离线依赖/` 支持无网安装，有版本锁 `requirements.lock`
- **LE**：**同时装了 `mujoco-js@0.0.7`（已被 npm 标记 deprecated）和官方 `mujoco@3.1.16`，但代码 `import` 的是前者**（`SimulationView.tsx:6`）——真实技术债。更严重的是**资产完全无治理**：`public/` 378MB 原样进构建产物（`dist/` 424MB），仅 MP600 就 288MB（含 92.9MB `.stp`、43.7MB `.dae`、40.9MB `.zip`），无压缩/LOD/glTF 流水线，**无逐资产来源与许可元数据**。且资产目录是**代码而非数据**——加一台机器人必须改 `src/data/robotCatalog.ts` 并重新构建

### 3.4 三个比"空壳"更严重的问题（实测发现）

**① 换机器人只换壳，规划永远算 ER15 —— 语义裂缝**

- 请求体 `PlanningRequest` **不带 robot id**（`src/types.ts:82-89`）
- 后果：**在 Define 面板切到 KUKA / T12A，3D 里看到的是那台机器，但规划用的仍是 ER15 的运动学与限位**

这是"界面上看不出来、但结果全错"的一类缺陷，比缺功能更难发现。附带证据：ER15 的限位表被**复制了 3 份**（`DesignPlugin.tsx:23-30`、`robotCatalog.ts:26-33`、`planning_bridge.py:56-63`），且前端展示的关节限位与所选机器人无关（`DesignPlugin.tsx:353-388`）。

**② 健康检查是死的 —— 守卫形同虚设**

> 📌 对照：驭臂的同类机制是真的——24 项接口自检**查的是形状**（签名含参名、dataclass 字段集、基类关系、属性可写性），失败会列出"该改我们这边：<文件>"，且**不中断启动**。

**③ 文档描述了一套代码里不存在的架构**

`docs/ALGORITHM.md:15-28` 声称有"Node 边车编排的五阶段流水线"，每阶段返回 `stage/status/durationMs/errorCode`，请求含 `algorithm.strategyId`（`:53-54`），响应含 `algorithmMeta`/`stageMetrics`/`debugLogs`（`:58-60`）。

**实测：这些标识符在 `src/ server/ scripts/` 全量搜索 0 命中，只存在于那份 .md 里。** 真实的分段逻辑全在一个 Python 函数内部（`pipeline.py:696-746`），Node 层不做任何编排。另外 `algorithm.strategyId`（文档承诺的算法可替换接口）**在代码里根本不存在**。

### 🟡 三级：能力天花板

10. **物理缺失**——只做正运动学，永远无法验证控制器稳定性（见 §2.1）。

12. **无数据录制回放**——只有规划结果回放。

## 六、跟你原始目标的差别（这是最重要的一节）

### 6.1 你的原始目标是什么

### 6.3 但 LE 揭示了你路线里的一个真问题

你选方案 C（站在官方肩膀上）时，判断依据是"**官方已经把发动机、变速箱、仪表盘都做好了，甚至留好了改装接口**"（`驭臂_完整工作报告.md:296`）。

## 七、建议

### 7.1 立刻可做的（低成本、高确定性）

1. **抄它的产品叙事，不抄它的界面**：把驭臂的面板重排成**任务流**（如"定义 → 规划 → 验证 → 辨识 → 部署"），而不是按功能平铺。**这是零代码量收益**——你的面板注册表 `面板注册表.py` 已经能做分组/可见性。
2. **别碰它的 Deploy/Monitor 写法**：那里全是假数据，照抄会把"演示感"带进真软件。
3. **认真考虑它证明的那件事**：它证明了"Web 外壳"在 3850 行内可跑。你原来的估算 5700~9000 行、2~4.5 人月，若把驭臂的算法层（真物理、辨识、录制）通过**边车进程**暴露给 Web 前端——**这就是 LE 的架构**（Node 边车 + Python 子进程），你已经有一个能跑的参考实现摆在这儿了。

### 7.2 要警惕的

4. **不要因为界面自卑而否定驭臂的底座**：出错隔离、24 项接口合同、真物理、参数辨识——这四样 LE 一样都没有，且都不是短期能补的。
5. **不要把"界面像"当成"做完了"**：LE 的 5 个模块里 3 个是空壳。这个陷阱对你尤其危险，因为你的目标是④"能自己改"，而空壳没有可改的实质。
6. **别忘了你自我诊断的第一号缺口**：6 个算法全是关节空间/轨迹级，**没有任务判据**——"缺了任务，这套东西永远只能演示，不能比较、不能积累"（`别人的仿真软件怎么做…自检.md:29`）。LE 的"四步流"恰好提示了任务的形状，但它的任务也是假的。

### 7.3 一句话总结

> **LE 是你路线图上"换外壳"那一格的廉价样机，不是替代品。**
> 它的界面值得学（尤其产品叙事），它的架构值得抄（边车 + Web 前端 + Python 算法），
> 但它的功能、工程纪律和许可证状况都不足以成为你的底座。
> **你的护城河是真物理 + 参数辨识 + 工程纪律；你的短板是界面和任务叙事——而这两样，LE 刚好各提供了一个可用的答案。**

## 八、融合方案结论（2026-10-16 追加）

> 以下是"驭臂 × LE 融合"的完整调查结论。详细论证见第八部分（§A~§E）。

1. **界面能部分脱离，而且"部分"正是最优解**——把二维界面搬到 Web，3D 视口留在原生。理由：驭臂的数据层（7 个桥接层 + 纯 dataclass 消息）**已经天然无界面耦合**，接缝现成；而 3D 留在原生既能保住 Filament 画质，又不用重做 LE 那种没有动力学的回放。
2. **LE 值得搬的功能只有一个**——TOPPRA+MVC+分段 Ruckig 的**时间最优轨迹规划**。它的 Deploy / SystemMonitor / Diagnose 全是假数据，不该抄；其余能力驭臂**本来就更强**（逐项见 §D.3）。
3. **移植有一个必须先决策的坑**——TOPPRA 默认求解器 `ecos` 是 **GPLv3**，与你 MIT 发布的意图冲突。**已实测找到解法**：改用 TOPPRA 自带的 `cvxpy` 接口 + Clarabel（Apache-2.0），数值结果**完全一致**，代价是**慢约 32 倍**（离线规划可接受）。
4. **在"要跨平台、Windows 优先"这个前提下，"单窗口原生 3D + Web 面板"只剩一条路**——**自建原生宿主**（§E.3 路线①）。因为 Filament 渲染器**不能被外部程序创建**（实测：所有后端都崩在 `Renderer` 构造），所以窗口层必须由自己掌控；而 macOS 专属的低成本捷径（PyObjC/WKWebView）对你的跨平台目标**不适用**。这条路"贵"，但它与跨平台需求**重合**，不是额外成本。

## A. 界面能否"部分脱离"宿主框架

### A.1 先说结论

**能，而且"部分脱离"是正确的切入点——但不是把 3D 也搬走。**

关键判断来自一个此前没被点明的架构事实（见 8.2）：**驭臂的数据层已经天然与界面解耦了**。界面难改的根因不在驭臂自己的代码，而在"官方 ImGui 是唯一的显示出口"这一点上。把显示出口开一个旁路，界面问题就绕过去了。

**3D 视口建议保留原生（Filament）**，二维界面（面板/参数/曲线/流程导航）搬到 Web。理由见 8.4 的方案对比。

### A.2 决定性证据：数据层已经是"无界面"的

这是本次调查最有价值的发现，它把"能不能脱离"从猜测变成了工程判断。

| 事实 | 证据 | 含义 |
|---|---|---|
| 官方消息模块是**纯 Python dataclass**，不是 C++ 扩展 | `messages.py`（Python 文件）；`StepEvent` 字段 = `['model','data']` | 消息可以被打包成 JSON 送到任意前端 |
| 7 个桥接层**完全没有 imgui 调用** | `指标桥.py`/`参数桥.py`/`模型桥.py` 的 `grep imgui` 均为 **0**；只 import `messages` 的 dataclass | 桥接层不需要图形上下文即可运行 |
| 算法层**不依赖任何界面模块** | `算法库/通用/*.py` 只 import `插件系统`/`参数辨识`/`录制桥`/`辨识桥`，无 `imgui`/`dear_imgui` | 控制算法可以脱离界面独立运行 |
| 快照消息自带 **latest-wins 丢弃策略** | `messages.Snapshot` docstring："Each new snapshot replaces the previous one… Intermediate values may be silently dropped" | 正是"以某个频率喂外部界面"所需的语义，不用自己造 |
| 全项目**唯一**碰官方实验 API 的文件是 `插件系统.py` | `软件/插件系统.py:2, 30-60`；`官方向口清单.py:33-48` 列出 13 个允许模块 | 官方依赖已被收敛到一点，替换出口不影响别处 |

**换句话说**：驭臂现在的形态是

```
[物理/算法/桥接：纯 Python + dataclass 消息]  ←── 已经是干净的、无界面的
                    ↓ 只能经由
        [官方 ImGui 绘制层：唯一的显示出口]  ←── 全部痛苦都在这一层
```

**要做的不是重写下面那层，而是给上面那层再开一个出口。**

### A.3 宿主框架到底锁死了什么（你已实测过的清单）

这部分直接引用你自己的实验记录，说明"为什么必须绕出去"而不是继续在框架内周旋：

### A.4 三条候选路线

| | 方案 A：全原生 | 方案 B：旁路 Web 界面（推荐） | 方案 C：纯 Web + 自研 3D |
|---|---|---|---|
| **3D 视口** | 官方 Filament（原生窗口） | 官方 Filament（原生窗口，保留） | three.js（浏览器） |

| **物理** | MuJoCo 原生 | MuJoCo 原生（不动） | MuJoCo 原生或 WASM |
| **算法** | 原生 | 原生（不动） | 原生（不动） |
| **脱离程度** | 0% | **部分脱离（二维层完全自由）** | 完全脱离 |
| **3D 画质** | ★★★★★ | ★★★★★（不变） | ★★★（three.js 弱于 Filament，LE 已印证） |
| **跨平台** | ❌ 仅 macOS | ❌ 3D 部分仍绑 macOS | ✅ 理论全平台 |
| **风险** | 已到天花板 | **中**：需要新增一条消息出口 | **高**：3D 要重写，且失去 Filament |
| **工作量** | — | 见 8.5 | ≈ LE 的 3850 行，且要补 3D |
| **能否复用现有界面代码** | — | ❌ 面板要重写（但逻辑可复用） | ❌ 同左 |

**推荐方案 B**，理由：

1. **它绕过的正是全部痛苦来源**——二维界面不再经过 ImGui，8.3 那张表的限制**一条都不再适用**（自由配色、动画、字体、布局、键盘可达性、i18n 全部可得）
2. **它不牺牲你唯一的护城河**——真物理、参数辨识、录制、Filament 3D 全部保留原样
3. **它的接缝已经存在**——桥接层是纯 dataclass，只需要"再加一个订阅者"
4. **它可增量推进**——可以先接一个面板试水，不必一次重写

接缝的落地细节见 §C（官方 Web 栈实测不可用，正确做法是在桥接层新增消息出口）。

**方案 C 不推荐**的原因很直接：LE 已经用 3850 行证明了纯 Web 外壳可行，但它的 3D 是 `mj_forward` + `three.js` 的**运动学回放**，你对照报告 §2.1 已确认它**没有动力学**。你要保留真物理，就得保留 Python 侧的 MuJoCo；既然如此，3D 也留在原生最省事，且画质更好。

## B. 移植 LE 的轨迹规划算法：可行性调查

> **这一节同时回答两个问题**：对问题②它是"唯一值得搬的功能"的详细成本核算（其余功能的取舍见 §D）；对问题①它是"新界面要展示什么"的输入。
>
> 结论是 LE 相对驭臂**唯一实质的功能优势**（见 §D.3），所以要单独调查。

### B.1 结论

**可行，但必须改变它的使用方式**——不能把它的输出直接接到 `ctrl[:]` 上，要把它当"离线轨迹生成器"，输出交给驭臂已有的跟踪控制器。

三个必须知道的前提（下面 9.2-9.4 逐条取证）：

1. **依赖可装**：`toppra`/`ecos` 在 macOS arm64 + Python 3.10 上**当场编译成功**（本次实测，见 附录 2）
2. **`numpy<2.0` 不是硬限制**：算法里**没有**任何 NumPy 2.0 移除的 API（实测 grep 为空），这个上界是保守写法，**未发现硬性阻塞**
3. ⚠️ **有一个许可证问题**：TOPPRA 默认求解器 `ecos` 是 **GPLv3**（详见 9.5）

### B.2 算法的真实依赖边界

`pipeline.py`（主算法）的实际依赖极少：

| 依赖 | 是否核心必需 | 说明 |
|---|---|---|
| `numpy` / `pandas` | ✅ 必需 | 数值与 CSV 读取 |
| `toppra` | ✅ 必需 | `pipeline.py:9-11` 模块级 import（`ta` / `algo` / `constraint`）——**硬依赖** |
| `ruckig` | ✅ 必需 | `pipeline.py:461, 468` 函数内 import，做 jerk 受限整形 |
| `scipy` | ✅ 必需 | TOPPRA 的约束构造 |
| `roboticstoolbox` / `spatialmath` | ⚠️ **只用于"拿机器人模型"** | 不在算法包里 import，只在 `scripts/planning_bridge.py:54` 的 `build_er15_robot_model()` 里用——**移植时可整块替换成 MuJoCo 的 FK** |

> 📌 **这是好消息**：`roboticstoolbox`（依赖链很长，还会拉 `xacrodoc`/`rospkg`/`pre-commit` 等 ROS 相关包）**不是算法核心依赖**。驭臂已有 MuJoCo，用 `mj_forward` 就能替代它。

**算法包的模块级依赖**（`fixed_toppra_mvc_ruckig/*.py`）：

- `pipeline.py`：`numpy`、`pandas`、`toppra`（`import toppra as ta` / `toppra.algorithm as algo` / `toppra.constraint as constraint`）
- `cli.py` / `example_usage.py`：额外用 `roboticstoolbox`——**这两个是 CLI/示例，移植时不需要**

**6 轴硬编码**：存在。CSV 必须有 `J1..J6` 表头（`pipeline.py:112, 120-123`），限位校验强制 6 值（`scripts/planning_bridge.py:96-97`），`cli.py:28-29` 还有断言。移植时要参数化（驭臂有 7 轴的 iiwa14 和 2 轴的 MP600 夹爪）。

### B.3 输出在"路径参数 s 空间"而非关节空间（最关键的语义问题）

`pipeline.py:39-42` 定义 `v_max / a_max / j_max`——**这三个量作用在路径参数 s 上，不是关节量**。Ruckig 那一段做的是"对 s 做 1-DoF 的 jerk 受限整形"（`:478-541`）。

**这意味着**：算法返回的 `qds`/`qdds`（`pipeline.py:677-678` 由 `np.gradient` 算出）是**关节空间的速度/加速度**没错，但**生成它们时的约束是在 s 空间施加的**。"关节速度约束"这个界面标签与它的实际作用域不一致（这也是 LE 自己的问题，见 §2.4.1）。

**对驭臂的含义**：不能把规划结果当作"每步直接写 `ctrl[:]` 的指令"。正确做法是：

```
LE 算法（离线）→ 时间参数化关节轨迹 (t, q, qd, qdd)
                        ↓
驭臂新增一个"轨迹跟踪"插件：读当前 t → 取期望 q → PD 跟踪 → 写 ctrl[:]
```

这条路径的好处是**完全复用驭臂已有的东西**：`算法库/通用/关节pd控制.py` 就是现成的跟踪控制器，`末端两点运动.py` 已经在做"走到目标"的闭环（实测末端误差 0.54 mm）。

**反过来做（把 s 空间的速度直接喂给 MuJoCo）会错**——MuJoCo 期望的是力矩或位置指令，语义完全对不上。

### B.4 与驭臂模型库的对接

| 需要什么 | LE 怎么拿 | 驭臂怎么拿 |
|---|---|---|

### B.5 ⚠️ 许可证问题（移植前必须决策）

| 组件 | 许可证 | 影响 |
|---|---|---|
| `toppra` 0.6.3 | **MIT**（包内 `LICENSE` 实测） | ✅ 可自由再分发 |
| `ruckig` 0.19.4 | **MIT**（PyPI 元数据实测） | ✅ 可自由再分发 |
| **`ecos` 2.0.14** | **GPLv3**（包内 `LICENSE` 实测） | ⚠️ **TOPPRA 的默认求解器**（`pipeline.py:34` 写死 `solver_wrapper: str = "ecos"`） |

**风险说明（非法律意见）**：GPLv3 是传染性许可证。驭臂当前是 **MIT**（已发布到 GitHub），如果把 GPLv3 组件作为**分发的整体**的一部分，通常要求整体按 GPLv3 分发。你正在把软件发给别人，所以这条必须处理。

**⚠️ 本次实测否掉了"换求解器"这条看似最省事的路**：

TOPPRA 名义上支持 4 种求解器（`ecos` / `qpoases` / `hotqpoases` / `seidel`，见 `reachability_algorithm.py:71,100,106,114,120`）。但实测把求解器换成 `seidel` 后**直接失败**：

```
✓ ecos    5.05s  时长=16.370s  点数=16371  末点q=[0.8, -0.5, 1.46]
✗ seidel  失败  AssertionError: Problem has conic constraints, solver seidel is not suitable
```

**根因**：算法在 TOPPRA 的关节约束外**又包了一层 `RobustLinearConstraint`**（`pipeline.py:296-300`，参数 `du=1e-3, dx=5e-2, dc=9e-3`），这产生了**二阶锥约束**，只有 `ecos` 这类锥求解器能处理。`seidel` 是线性规划求解器，结构上不适用。

> 📌 这个约束是算法**质量的一部分**（鲁棒化处理），不是可以随手删掉的装饰——所以"换个求解器就绕开 GPL"是**不成立**的。这提高了移植的决策难度，必须正面处理。

**✅ 本次实测：这条路走通了，但有速度代价**

装 `cvxpy 1.7.5`（Apache-2.0）+ `clarabel`（Apache-2.0）后，把 `solver_wrapper` 改成 `"cvxpy"` 重跑同一组样例：

| 求解器 | 许可证 | 耗时 | 轨迹时长 | 与 ecos 结果差异 |
|---|---|---|---|---|
| `ecos`（现状） | ⚠️ GPLv3 | **5.19 s** | 16.370 s | 基准 |
| `cvxpy` + Clarabel | ✅ Apache-2.0 | **164.91 s** | 16.370 s | **完全一致（时长差 0.0000s，关节角差 0.000000 rad）** |

**结论**：
- **数值上完美等价**——同样的轨迹时长、同样的 16371 个采样点、关节角零偏差
- **但慢约 32 倍**（5s → 165s）。原因是 cvxpy 在每个网格点（共 1000 点）上重建并规范化优化问题，开销累积（运行中提示 "This code path has been hit 174875 times"）

**这对你的含义**：作为**离线轨迹生成**（点一次"规划"、等 2-3 分钟出一份轨迹）是可接受的，而且完全不影响你 MIT 发布的自由；作为**交互式实时规划**则不可接受。

因此建议的路线是：**先用 cvxpy+Clarabel 保证许可证干净**（默认路径），把性能优化留作后续（要么调 cvxpy 的求解器选项，要么并行化网格点，要么在有明确需要时再评估）。

**三条真正可选的处理**：

| 方案 | 做法 | 代价 | 评价 |
|---|---|---|---|
| **① 把 GPLv3 组件当"独立进程"用** | ecos 只作为独立 Python 进程内的库被调用，不与你的软件静态链接；在文档中明确声明依赖及其许可证 | 需要法务判断"聚合"边界；通常认为是较弱的主张 | ⚠️ 有争议，非法律意见，建议咨询后再定 |
| **② 改用宽松许可证的锥求解器（✅ 已实测走通）** | **不需要改算法代码**——TOPPRA 自带 `cvxpy_solverwrapper.py`，只需把 `ToppraConfig.solver_wrapper` 从 `"ecos"` 改成 `"cvxpy"`（`pipeline.py:34` 一个字段），再用 cvxpy 的 **Clarabel**（Apache-2.0）后端求解 | **几乎为零的代码改动**；代价是**速度**（见下） | ✅ **推荐**。已实测数值完全等价 |
| ③ 整个软件改 GPLv3 | 接受传染 | 与你"让人合作/被广泛采用"的目标冲突 | ❌ 不推荐 |
| ④ 保持 MIT，不捆绑 ecos | 用户自行安装 | 破坏开箱即用 | ⚠️ 退路 |

> ⚠️ 以上为技术分析，**不是法律意见**。GPL 的义务只在**分发**时触发（自己用不受限），但你已把软件发到 GitHub，所以按"要分发"规划。建议在动手前确认一次。

## C. Web 接缝的施工图：怎么接、风险在哪

### C.1 先否掉"修好官方 Web 栈"这条路

调查中曾希望直接复用官方的 Web 能力（`ViewerConfig.gfx='web'`），因为官方文档写着"launches Web Viewer"。**实测结论：这条路不通，而且有三个独立的死结**（注意：不是缺 `web_viewer.py`——它在，缺的是它依赖的两个 C++ 扩展）：

| 死结 | 证据 | 说明 |
|---|---|---|
| **① 缺 C++ 扩展** | `web_viewer.py` **存在**（`studio/web_viewer.py`，15KB），但它 import `headless_ui` / `state_payload` 两个扩展，二者在 wheel 内**都不存在**：实测 `ImportError: cannot import name 'headless_ui' from 'mujoco.experimental.studio.web'` | 缺的是 **NetImgui 桥接与状态序列化的原生模块**，不是 Python 文件。这也解释了为什么 `/state` 的 payload 无法自行构造——生成它的代码在缺失的扩展里 |
| **② 缺前端产物** | `web_server.py:341-343` 找 `web/dist`；wheel 里没有 dist，也没有任何 `.wasm`/`.js` | dist 由 **Emscripten 构建**产生（`web_server.py:326` 注释），官方不分发 |
| **③ 服务端自己不启动** | `WebServer.start()`（`web_server.py:1133-1135`）**第一句就是** `if not self.static_files_dir: logger.warning(...); return` | **没有 dist 目录，服务端静默不启动**——连 `/state` 都不会广播 |

补一条：`/ui` 通道桥接的是 **NetImgui 二进制协议**（`web_server.py:19-22` 注释："serves the bridge to the headless NetImgui client"）。这是未文档化的专属协议，自研前端无法实现它。

> 📌 你在 `文档/驭臂_完整工作报告.md:814`（F11）的判断**是对的**，且本次复核确认了**更根本的原因**：不只是 `ImportError`，而是**服务端在没有 dist 时会主动拒绝启动**。所以"修官方 Web 栈"= 要自建 emsdk 工具链 + 逆向 NetImgui 协议，**性价比极低**。

## E. 界面方案的决定性约束与跨平台布局

> **这一节回答用户明确提出的界面构想**：3D 视口保持原生 Filament，周围面板用 Web 技术，视觉上是**一个完整窗口**（用户比喻为"切片面包表面镶嵌一块葡萄"）。
> **附加约束（用户 2026-10-16 补充）**：软件**必须跨平台**，且**未来主要用户可能是 Windows**；本期不做兼容工程，但**架构必须为跨平台留出空间**。

### E.1 结论

**用户的构想可实现，但只能"自建原生宿主"这一条路——而这条路的起点，恰好与跨平台需求重合。**

两个关键技术障碍（均经实测确认，见 E.2）排除了所有"低成本捷径"：

- Filament 渲染器**不能被外部程序创建**，必须依附官方窗口
- ImGui 绑定**无法接收网页纹理**，网页画不进 3D 窗口

因此**纹理共享路线整体不可行**，唯一可行的是**"窗口服务器级组合"**——3D 视图与 Web 视图是**同一窗口内的兄弟视图**，由系统合成，不交换纹理。

### E.2 两个致命约束（实测证据）

**约束一：Filament `Renderer` 不能在外部构造**

本次实测了全部渲染后端，**全部崩在 `Renderer` 构造阶段**：

```
S1 装载模型…                    ✓
S2 模型 OK，构造 Renderer…
ERROR: Failed to open filament asset 'pbr.filamat'
（退出码 1，进程直接终止）
```

测试覆盖 `classic` / `classic_headless` / `opengl` / `opengl_headless` / `vulkan` 等模式，并已排除两种干扰因素：
- **不是资产路径问题**：设置了官方环境变量 `MUJOCO_STUDIO_ASSETS_DIR`（发现于 `web_viewer.py:65`）后仍然崩溃
- **不是缺资产文件**：`assets/` 下 `pbr.filamat` 等文件齐全
- **不是模式名错误**：合法值取自官方 `viewer_protocol.GFX_MODES`（其中**没有** `filament` 这个名字）

**根因**：官方**不在外部构造渲染器**，而是在窗口内部完成——
```
native_viewer.py:98    self._viewer.InitRenderer(model)
```
即 **Renderer 归窗口所有、由窗口创建**。所以"自己起一个离屏渲染器、把画面喂给别处"这条路**堵死**。

> ⚠️ **勘误（对本报告前文的更正）**：§C.1 曾写"缺 `web_viewer.py`"，**这是错的**——`web_viewer.py` 存在于 `studio/web_viewer.py`（15KB），当时只查看了 `studio/web/` 子目录。真实的失败原因是它 import `headless_ui` / `state_payload` 两个 **C++ 扩展**，而这两个在 wheel 内不存在（`ImportError: cannot import name 'headless_ui'`，与 `文档/驭臂_完整工作报告.md:814` 的 F11 原始判断一致）。**结论不变，但原因已更正。**

**约束二：ImGui 无法接收网页纹理**

| 检查项 | 实测结果 |
|---|---|
| `Image` / `ImageButton` | ✅ 存在，但签名要求 **`user_texture_id`**（一个已存在的纹理 ID） |
| `Texture` / `Render` / `Draw` / `Framebuffer` | ❌ **全部不存在**（imgui 绑定共 315 个符号，无任何纹理创建/上传接口） |

所以"把网页渲染成纹理再贴进 3D 窗口"在 Python 层**做不到**，除非改 C++。

### E.3 三条可行路线与工程量

| | 做法 | 达成效果 | 工程量 | 跨平台 |
|---|---|---|---|---|
| **① 自建原生宿主（推荐）** | 不用 MuJoCo Studio，自己做宿主窗口：内嵌 MuJoCo+Filament 渲染 3D + 系统 WebView 做面板 | ✅ **完全实现构想** | **最大**（等于重写 Studio 窗口层） | ✅ WebView2/WKWebView/WebKitGTK 三家都有 |
| ② 打补丁改官方 Studio | fork MuJoCo 源码，把 ImGui 面板区换成 WebView | ✅ 实现构想 | 大（需重编 `native_viewer_cc.so`） | ❌ 上游 experimental 层只保 macOS；且 11 周改过 4 次结构，维护成本高 |
| ③ 同进程原生视图叠加 | 用 PyObjC 取官方 Cocoa 窗口，把 WKWebView 作为子视图贴上去盖住面板区 | ⚠️ 看上去是构想的样子 | 小（数百行 Python） | ❌ **macOS 专属**（PyObjC/WKWebView）→ **对跨平台目标不适用** |

> 📌 **为什么必须放弃 ③**：它是本次调研中**成本最低**的方案（几百行 Python、不用改 C++），但它是**纯 macOS 技术**。既然目标是跨平台、且 Windows 优先，**采它等于把最贵的返工留到以后**。
>
> 📌 **为什么 ① 的"贵"是不可避免的**：因为约束一（Renderer 归窗口所有）意味着**窗口层必须由自己掌控**才能谈组合。官方 Studio 不提供"只要 3D、不要面板"的开关，所以自建宿主是唯一能把窗口层拿回来的方式。

### E.4 跨平台架构布局

**关键认识：驭臂最值钱的那一层，天然就是跨平台的。**

```
┌─────────────────────────────────────────────────────────────┐
│  ③ 界面层（Web 技术）                                        │
│     React/Vue/任意框架 + 业务代码                            │
│     ★ 天然跨平台：三家系统上是同一份代码                      │
├─────────────────────────────────────────────────────────────┤
│  ② 平台适配层  ← 需要为跨平台新写的部分（接口一旦定好就稳定） │
│     必须抽象出且只抽象出四个能力：                            │
│       a) 创建宿主窗口                                        │
│       b) 挂载系统 WebView（macOS: WKWebView /               │
│          Windows: WebView2 / Linux: WebKitGTK）              │
│       c) 获取 3D 视口矩形（供布局用）                         │
│       d) 让 3D 视图与 WebView 在同一窗口内组合                │
│     ★ 建议用 C++/Rust 写一次、三平台各编译一次                │
├─────────────────────────────────────────────────────────────┤
│  ① 数据/逻辑层  ← 驭臂已有，且已天然无界面耦合（见 §A.2）     │
│     物理 + 控制算法 + 7 个桥接层（纯 Python + dataclass）     │
│     ★ 跨平台阻力最小                                          │
└─────────────────────────────────────────────────────────────┘
```

**为跨平台"留出空间"的具体做法**（本期不必实现，但必须现在定形）：

1. **新增一个桥，不要新增耦合**：Web 界面只通过 §C.2 的"消息出口"与数据层通信，**绝不直接 import 界面或平台 API**
2. **平台相关代码全部收进 `平台适配层/` 一个目录**，用抽象接口（如 `宿主接口.py`）定义上面那四个能力；**业务代码永远不 import 系统 API**
3. **先只实现 macOS 一家**，但**接口从第一天就按"三平台"命名与签名设计**——这样 Windows 那次是"加一个实现"，不是"重构"
4. **Web 界面不要用任何平台特有 API**（如 Electron 专有接口），保持纯标准 Web

### E.5 一个必须提前考虑的风险

**跨平台的瓶颈可能不在界面，而在 `mujoco.experimental.studio` 本身。**

驭臂当前的分层是：**自己的外壳 → 官方实验层（`studio`）→ 官方 C++ 层**。而：

- `文档/驭臂_完整工作报告.md:717` 已把"Web 宿主 / Tauri / Electron"整行排除，理由之一就是 studio 层的限制
- 官方实验层（`studio`）长期只保 macOS：驭臂为 macOS 主线程限制做了整套线程对调（`软件/启动.py:6-14`）
- 代码里**未找到任何 `sys.platform` 降级分支**——换平台直接不成立（见 §2.3.1）

**所以如果 Windows 是目标，要重新评估的问题不只是"界面怎么放"，而是：**

> **官方 `studio` 层在 Windows 上到底能不能用？**

三种可能的结局，代价差一个数量级：

| 若 studio 在 Windows…… | 则工作量 | 说明 |
|---|---|---|
| 能用 | 只做界面层 + 平台适配层 | 最省 |
| 不能编译 | 要放弃 studio，直接用 MuJoCo 核心 + Filament 自建宿主 | **与路线 ① 合并**（反正 ① 本来就要自建宿主） |
| 能用但行为差异大 | 需要双实现，回到"平台适配层"内部消化 | 中等 |

**这应该作为跨平台工作的第一个调查项**（先于任何界面改造）——因为它决定路线 ① 是不是"顺便就把跨平台做了"，还是一件独立的大工程。

### E.6 待决策的检查点

在动手前应确认以下四项（本条为后续工作的入口）：

| # | 待确认 | 为什么关键 |
|---|---|---|
